title: Validation
description: Derive strict Zod or Valibot request and response schemas from a resource, see exactly what the parser defaults, and narrow the accepted contract per endpoint.
---

`requestSchema` turns a resource's field policy into a strict transport schema. `responseSchema` turns its relation tree into a schema for the rows it returns.

Both ship for Zod and for Valibot, from separate subpath exports. The two produce the same accepted payload and the same defaults — only the error objects differ.

## Choosing a validator

|         | Zod                      | Valibot                     |
| ------- | ------------------------ | --------------------------- |
| Import  | `drizzle-resource/zod`   | `drizzle-resource/valibot`  |
| Peer    | `zod` `^4.4.3`           | `valibot` `^1.4.2`          |
| Parse   | `schema.safeParse(body)` | `v.safeParse(schema, body)` |
| Failure | `error.issues`           | `issues`                    |

::code-group

```bash [Zod]
npm install zod
```

```bash [Valibot]
npm install valibot
```

::

::warning
Zod 3 does not work. The request schema is built from `z.strictObject` and Zod 4 internals.
::

## The request schema

Pass the resource. The schema inherits its field registry, search and facet allow-lists, sortable paths, pagination modes, defaults, and limits:

```ts twoslash [orders.schema.ts]
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource } from "./orders.resource";

export const ordersRequestSchema = requestSchema(ordersResource);

const request = ordersRequestSchema.parse({
  filters: [{ type: "condition", key: "status", operator: "isAnyOf", value: ["pending"] }],
  search: { value: "ORD", fields: ["reference"] },
});

console.log(request.pagination.pageSize);
```

Valibot takes the same resource and produces the same contract, with the parse function moved to the outside:

```ts twoslash [orders.schema.ts]
import { requestSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./orders.resource";

export const ordersRequestSchema = requestSchema(ordersResource);

const request = v.parse(ordersRequestSchema, {
  filters: [{ type: "condition", key: "status", operator: "isAnyOf", value: ["pending"] }],
  search: { value: "ORD", fields: ["reference"] },
});

console.log(request.pagination.pageSize);
```

Neither schema accepts `context`. The transport payload is client input, and context is server input — see [HTTP Endpoints](/integration/http-endpoints).

## What the parser fills in

Every top-level key is optional, so `{}` parses. The schema then substitutes the resource's own configuration rather than a generic fallback:

| Client sends                 | Result                                                                     |
| ---------------------------- | -------------------------------------------------------------------------- |
| no `pagination`              | the full default pagination object, built from `query.defaults.pagination` |
| `pagination` without `count` | `"exact"` for offset, `"none"` for cursor                                  |
| `sorting: []`                | the resource's `sort.defaults`                                             |
| `search.fields: []`          | the resource's `search.defaults`                                           |
| no `filters`                 | `[]`                                                                       |
| no `facets`                  | omitted entirely — the facet stage never runs                              |

Parsing `{}` against the example orders resource produces a complete request:

```json
{
  "pagination": { "mode": "cursor", "cursor": null, "pageSize": 25, "count": "none" },
  "sorting": [{ "dir": "desc", "key": "createdAt" }],
  "filters": [],
  "search": { "value": "", "fields": ["reference", "customer.name"] }
}
```

That resource declares `defaults.pagination: { mode: "cursor", pageSize: 25 }`, `sort.defaults: [{ key: "createdAt", dir: "desc" }]`, and `search.defaults: ["reference", "customer.name"]` — the parser copied all three.

::note
The empty-array fallbacks are substitutions, not merges. `sorting: [{ key: "totalAmount", dir: "asc" }]` replaces the resource default outright; it does not append to it.
::

## Every level is strict

The request object, the pagination object, each sort descriptor, each filter node, and each facet request are all `strictObject`. An unknown key anywhere is a parse error, not a silently dropped field:

```ts twoslash
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource } from "./orders.resource";

const ordersRequestSchema = requestSchema(ordersResource);

const parsed = ordersRequestSchema.safeParse({
  sorting: [{ key: "createdAt", dir: "desc", nulls: "last" }],
});

if (!parsed.success) {
  console.log(parsed.error.issues[0].code);
  // "unrecognized_keys"
}
```

Valibot reports the same rejection through its issue list:

```ts twoslash
import { requestSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./orders.resource";

const ordersRequestSchema = requestSchema(ordersResource);

const parsed = v.safeParse(ordersRequestSchema, { context: { orgId: "acme" } });

if (!parsed.success) {
  console.log(parsed.issues[0].message);
  // Invalid key: Expected never but received "context"
}
```

Strictness is what makes the payload a contract. A client that renames a key learns immediately instead of quietly losing a filter.

## Field and value rules

Field names are checked against the resolved contract, not against the raw schema. A path that the resource hid, disabled, or left out of an allow-list is rejected by the parser before the engine ever sees it.

| Rule                                  | Zod message                            | Valibot message                                   |
| ------------------------------------- | -------------------------------------- | ------------------------------------------------- |
| `pageSize` must be a positive integer | `Too small: expected number to be >0`  | `Invalid value: Expected >=1 but received 0`      |
| `pageSize` at most `maxPageSize`      | `Too big: expected number to be <=100` | `Invalid value: Expected <=100 but received 5000` |
| sort key must be sortable             | `Sorting field is not allowed`         | `Sorting field is not allowed`                    |
| filter key must be in the registry    | `Filter field is not allowed`          | `Filter field is not allowed`                     |
| search field must be allowed          | `Search field is not allowed`          | `Search field is not allowed`                     |
| facet key must be allowed             | `Facet field is not allowed`           | `Facet field is not allowed`                      |
| pagination mode must be allowed       | `Pagination mode is not allowed`       | `Pagination mode is not allowed`                  |

Sortable means the path contains no `many` step, so `tags.name` and `orderLines.product.name` fail this check even though both are perfectly good filter and search fields.

## Narrowing an endpoint

Pass an override as the second argument to restrict one route below the resource policy. `allow` accepts `filters`, `sorting`, `search`, `facets`, and `pagination`:

```ts twoslash [public-orders.schema.ts]
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource } from "./orders.resource";

export const publicOrdersRequestSchema = requestSchema(ordersResource, {
  allow: {
    filters: ["status", "customer.name", "totalAmount"],
    sorting: ["createdAt", "totalAmount"],
    search: ["reference"],
    facets: ["status"],
    pagination: ["offset"],
  },
  defaults: {
    pagination: { mode: "offset", pageIndex: 1, pageSize: 20 },
  },
  limits: { maxPageSize: 50, maxFacetLimit: 20 },
});
```

The same override object works with Valibot:

```ts twoslash [public-orders.schema.ts]
import { requestSchema } from "drizzle-resource/valibot";

import { ordersResource } from "./orders.resource";

export const publicOrdersRequestSchema = requestSchema(ordersResource, {
  allow: {
    filters: ["status", "customer.name", "totalAmount"],
    sorting: ["createdAt", "totalAmount"],
    search: ["reference"],
    facets: ["status"],
    pagination: ["offset"],
  },
  defaults: {
    pagination: { mode: "offset", pageIndex: 1, pageSize: 20 },
  },
  limits: { maxPageSize: 50, maxFacetLimit: 20 },
});
```

An override can only narrow. Each `allow` list is intersected with the resource's own set, so naming a hidden path adds nothing, and each limit becomes the lower of the resource value and the override value. There is no way to widen a resource from a route.

Narrowing also trims the defaults it inherits. The example resource searches `["reference", "customer.name"]` by default, but this endpoint only allows `reference`, so its default search field list becomes `["reference"]`.

## Defaults are checked at schema-creation time

A default that falls outside the narrowed sets throws immediately, when the module loads — not on the first request that relies on it.

Narrowing `sorting` without moving the default sort key throws:

```ts
requestSchema(ordersResource, { allow: { sorting: ["totalAmount"] } });
// Error: Default sorting field "createdAt" is not allowed for resource "orders"
```

Narrowing `pagination` without moving the default mode throws the same way:

```ts
requestSchema(ordersResource, { allow: { pagination: ["offset"] } });
// Error: Default pagination mode "cursor" is not allowed for resource "orders"
```

::warning
This is the most common surprise when restricting an endpoint. The example resource defaults to cursor mode, so an offset-only route must override `defaults.pagination.mode` as well as `allow.pagination` — which is exactly what the narrowing example above does.
::

Failing at import means a broken route cannot deploy. A default sort key or default mode that the endpoint refuses is a configuration bug, and there is no sensible runtime fallback for it.

## Response schemas

`responseSchema` starts from Drizzle's `createSelectSchema` for the root table, then walks the resource's declared `relations` tree. A `one` relation becomes nullable, a `many` relation becomes an array, matching the hydrated output.

Overrides nest the same way the relation tree does, and the inferred output type follows every transform:

```ts twoslash [orders.response.ts]
import { responseSchema } from "drizzle-resource/zod";
import { z } from "zod";

import { ordersResource } from "./orders.resource";

export const ordersResponseSchema = responseSchema(ordersResource, {
  columns: {
    totalAmount: (schema) => schema.transform((value) => (value / 100).toFixed(2)),
  },
  relations: {
    customer: {
      columns: { name: (schema) => schema.transform((value) => value.trim()) },
    },
    orderLines: {
      relations: {
        product: {
          columns: { sku: (schema) => schema.transform((value) => value.toUpperCase()) },
        },
      },
    },
  },
});

type OrdersResponse = z.infer<typeof ordersResponseSchema>;
type Order = OrdersResponse["rows"][number];

declare const order: Order;
order.totalAmount;
//    ^?
```

`totalAmount` was an integer on the row and is a string after the transform, and the inferred type says so.

Valibot expresses the same overrides through `v.pipe`, and `v.InferOutput` reads the result:

```ts twoslash [orders.response.ts]
import { responseSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./orders.resource";

export const ordersResponseSchema = responseSchema(ordersResource, {
  columns: {
    totalAmount: (schema) =>
      v.pipe(
        schema,
        v.transform((value) => (value / 100).toFixed(2)),
      ),
  },
  relations: {
    customer: {
      columns: {
        name: (schema) =>
          v.pipe(
            schema,
            v.transform((value) => value.trim()),
          ),
      },
    },
  },
});

type OrdersResponse = v.InferOutput<typeof ordersResponseSchema>;
type Order = OrdersResponse["rows"][number];

declare const order: Order;
order.totalAmount;
//    ^?
```

A response override changes parsing and output typing only. It does not change the selected columns, the SQL, or the field policy — those live on the resource.

The `pageInfo` union and the optional `facets` array are included for free, with the same four-way discrimination the engine returns.

::note
Validating a response on the server costs a full walk of every row. Most teams use `responseSchema` for its inferred types and for contract tests, and skip the runtime parse in production.
::
