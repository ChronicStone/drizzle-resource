An engine binds `drizzle-resource` to one Drizzle connection. Every resource is created from an engine and inherits its schema, relation graph, and context type.

## Creating an engine

Pass your database, schema, and relation graph — the same three objects your Drizzle setup already exports:

```ts twoslash [engine.ts]
import { createQueryEngine } from "drizzle-resource";

import { db } from "./db";
import { relations } from "./relations";
import { schema } from "./schema";

export const engine = createQueryEngine({ db, schema, relations });
```

The call does no I/O. It captures the three references and returns a factory, so an engine is safe to create at module scope.

[Installation](/getting-started/installation) covers what each of those three objects must expose.

## Which tables can be a root

A resource root must exist in **both** `db.query` and `schema`. The root key type is the intersection of the two, so a table missing from either is not offered by autocomplete and is rejected by the compiler.

That intersection is also the reason `relations` must be passed to `drizzle()`. Without it, `db.query` is empty and no table qualifies as a root.

::warning
`drizzle-resource` is Postgres only. The SQL compiler targets `drizzle-orm/pg-core`, and no other Drizzle dialect is supported.
::

## Typing the request context

Call `withContext` to declare the per-request data your scope functions and strategy overrides receive:

```ts twoslash [engine.ts]
import { createQueryEngine } from "drizzle-resource";

import { db } from "./db";
import { relations } from "./relations";
import { schema } from "./schema";

export const engine = createQueryEngine({ db, schema, relations }).withContext<{
  isAdmin?: boolean;
  orgId: string;
  userId?: string;
}>();
```

`ctx` is now typed in every `query.scope` callback on resources built from this engine, and a key that does not exist fails to compile:

```ts twoslash
// @errors: 2339
import { engine } from "./engine";
// ---cut-before---
engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    scope: (f, ctx) => f.is("customer.orgId", ctx.tenantId),
  },
});
```

Skip `withContext` and `ctx` is a plain `Record<string, unknown>` — the scope still runs, but a typo in a context key reaches production.

::note
`withContext` returns a **new** engine rather than mutating the existing one. Resources defined before the call keep the previous context type, so call it once where the engine is created.
::

## One engine, many resources

Create one engine per database connection and export it. Several resources can share a root table with different policies, such as a public resource and an internal one:

::code-group

```ts twoslash [engine.ts]
import { createQueryEngine } from "drizzle-resource";

import { db } from "./db";
import { relations } from "./relations";
import { schema } from "./schema";

export const engine = createQueryEngine({ db, schema, relations }).withContext<{
  isAdmin?: boolean;
  orgId: string;
}>();
```

```ts twoslash [orders.public.ts]
import { engine } from "./engine";
// ---cut-before---
export const publicOrders = engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    scope: (f, ctx) => f.is("customer.orgId", ctx.orgId),
    search: { allowed: ["reference"], defaults: ["reference"] },
    facets: { allowed: ["status"] },
  },
});
```

```ts twoslash [orders.internal.ts]
import { engine } from "./engine";
// ---cut-before---
export const internalOrders = engine.defineResource("orders", {
  relations: {
    customer: true,
    orderLines: { with: { product: true } },
  },
  query: {
    search: {
      allowed: ["reference", "customer.name", "orderLines.product.sku"],
      defaults: ["reference"],
    },
    facets: { allowed: ["status", "customer.billingCountry"] },
  },
});
```

::

Each resource builds its own field registry, so the internal one exposes `orderLines.product.sku` while the public one has no such path at all.

::note
`engine.defineQueryResource` is an alias of `defineResource`, kept for older code. New resources should use `defineResource`.
::

## Reusable scope handlers

`engine.defineScope` builds a scope callback outside a resource, so several resources can share one tenancy rule. Its argument order differs from an inline `query.scope` — see [Scope Rules](/resource-setup/scope#reusing-a-scope-across-resources).
