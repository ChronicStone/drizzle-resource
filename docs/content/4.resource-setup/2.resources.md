`engine.defineResource(root, options)` declares one query resource bound to one root table. It is the whole configuration surface of `drizzle-resource`.

This page owns the **shape** of `defineResource`. What a policy key means for an individual field path belongs to [Field Policy](/resource-setup/field-policy).

## One complete resource

Every key is optional. A resource that declares all of them looks like this:

```ts twoslash [orders.resource.ts]
import { engine } from "./engine";
// ---cut-before---
export const ordersResource = engine.defineResource("orders", {
  relations: {
    customer: true,
    orderLines: { with: { product: true } },
    tags: true,
  },
  query: {
    scope: (f, ctx) => (ctx.isAdmin ? undefined : f.is("customer.orgId", ctx.orgId)),
    filters: {
      hidden: ["customerId"],
      disabled: ["deletedAt"],
    },
    search: {
      allowed: ["reference", "customer.name", "orderLines.product.name", "orderLines.product.sku"],
      defaults: ["reference", "customer.name"],
    },
    sort: {
      defaults: [{ key: "createdAt", dir: "desc" }],
      disabled: ["customer.billingCountry"],
    },
    facets: {
      allowed: ["status", "customer.name", "orderLines.product.category", "tags.name"],
    },
    pagination: { modes: ["offset", "cursor"] },
    defaults: {
      pagination: { mode: "offset", pageIndex: 1, pageSize: 25, count: "exact" },
    },
    validation: {
      maxPageSize: 100,
      maxFacetCount: 6,
      maxFilterNodes: 40,
    },
  },
});
```

That declaration is the entire contract — the request shape, the response shape, and the validators all derive from it.

## `root`

The root is the table key, and it must exist in both `db.query` and your schema map. It fixes the row identity used by pagination, hydration, and facet counting: every stage keys on the root table's `id` column.

## `relations`

`relations` is a Drizzle `with` tree, and it does two jobs at once:

1. **Hydration** — it is passed straight to `db.query.<root>.findMany({ with })`, so it decides the row shape.
2. **Registration** — every column of every reachable table becomes a dotted field path such as `customer.name` or `orderLines.product.sku`.

Omit `relations` and the resource registers root columns only. Relation cardinality then changes what each path can do — a path crossing a `many` step is never sortable, which [Relation Model](/core-concepts/relation-model) covers in full.

## `query`

`query` holds the declarative policy. Each key is owned by a dedicated page:

::field-group
::field{name="scope" type="(filters, context) => QueryFilterInput"}
Server-side filters merged into every request, ahead of client filters. See [Scope Rules](/resource-setup/scope).
::
::field{name="filters" type="{ hidden?, disabled? }"}
Field paths removed from the registry. Both keys delete — see [Field Policy](/resource-setup/field-policy).
::
::field{name="search" type="{ allowed?, defaults? }"}
Searchable paths, and the paths used when the client sends `search.fields: []`. See [Text Search](/query-contract/search).
::
::field{name="sort" type="{ defaults?, disabled? }"}
Fallback sorting, and paths that may not be sorted on. A disabled key throws — see [Sort Order](/query-contract/sorting).
::
::field{name="facets" type="{ allowed? }"}
Facetable paths. A request for any other key is rejected. See [Facet Counts](/query-contract/facets).
::
::field{name="pagination" type="{ modes? }"}
Pagination modes this resource accepts. Defaults to `["offset"]`.
::
::field{name="defaults" type="{ pagination? }"}
Fallback pagination values applied during normalization.
::
::field{name="validation" type="ResourceQueryValidationConfig"}
Upper bounds on request complexity. See [Request Limits](/resource-setup/limits).
::
::

## `query.pagination`

Offset is the only mode enabled by default. Cursor pagination is opt-in, and enabling it means listing **both** modes if you still want offset:

```ts twoslash
import type { ExamplePaginationConfig } from "./twoslash-support";
// ---cut-before---
const pagination = { modes: ["offset", "cursor"] } satisfies ExamplePaginationConfig;
```

A request whose mode is not listed throws `Pagination mode "cursor" is not allowed for resource "orders"` before any SQL runs.

::warning
`modes: ["cursor"]` on its own throws at definition time. The default mode is `"offset"` unless you also set `defaults.pagination.mode`, and the default mode must be one of the allowed modes.
::

Restricting the modes means moving the default mode along with them:

```ts twoslash
import type { ExampleDefaultsConfig, ExamplePaginationConfig } from "./twoslash-support";
// ---cut-before---
// A cursor-only resource needs both keys
const pagination = { modes: ["cursor"] } satisfies ExamplePaginationConfig;
const defaults = {
  pagination: { mode: "cursor", pageSize: 50 },
} satisfies ExampleDefaultsConfig;
```

Cursor mode also requires a visible, sortable root `id` — [Pagination](/query-contract/pagination) explains why the engine needs that tiebreaker.

## `query.defaults`

`defaults.pagination` fills the gaps left by the transport payload:

| Key         | Effect                                                 | Fallback                          |
| ----------- | ------------------------------------------------------ | --------------------------------- |
| `mode`      | Mode a validator assumes when `pagination` is omitted  | `"offset"`                        |
| `pageIndex` | Used when the incoming `pageIndex` is zero or negative | `1`                               |
| `pageSize`  | Used when the incoming `pageSize` is zero or negative  | `25`                              |
| `count`     | Count policy for the default mode only                 | `"exact"` offset, `"none"` cursor |

`count` is deliberately narrow: it applies only when the request's mode equals `defaults.pagination.mode`. An offset default of `count: "none"` therefore leaves cursor requests untouched.

::caution
Set fallback sorting in `query.sort.defaults`, not in `query.defaults.sorting`. The engine reads sort defaults from `query.sort.defaults` only — the `defaults.sorting` field exists on the shared defaults type but is never read at resource level.
::

## `query.validation`

`validation` caps request complexity, and the engine enforces it on every call whether or not a validator ran:

```ts twoslash
import type { ExampleValidationConfig } from "./twoslash-support";
// ---cut-before---
const validation = {
  maxPageSize: 50,
  maxFilterNodes: 30,
} satisfies ExampleValidationConfig;
```

Unset keys fall back to the package defaults. [Request Limits](/resource-setup/limits) lists all six with the exact error each one throws.

## `strategy`

`strategy` replaces one stage of the pipeline with your own implementation while keeping the request and response contract intact. Start without it — see [Strategies](/resource-setup/strategies).

## What a resource exposes

The returned object is both the query surface and the introspection surface:

| Member                                       | Purpose                                                                  |
| -------------------------------------------- | ------------------------------------------------------------------------ |
| `key`                                        | The root table key                                                       |
| `schema`                                     | The engine's schema map                                                  |
| `relationGraph`                              | The engine's relation graph                                              |
| `relations`                                  | The declared `with` tree, as passed to hydration                         |
| `fields`                                     | `Map<string, FieldRegistryEntry>` — the registry after policy is applied |
| `queryConfig`                                | Normalized policy, including resolved `validation` limits                |
| `query` `queryIds` `queryRows` `queryFacets` | The four query methods                                                   |

Reading `fields` is the reliable way to confirm a policy did what you expected:

```ts twoslash
import { ordersResource } from "./twoslash-support";
// ---cut-before---
// `deletedAt` is in `filters.disabled`, so it is not in the registry at all
const isRegistered: boolean = ordersResource.fields.has("deletedAt");
const isSortable = ordersResource.fields.get("tags.name")?.sortable;
```

A missing entry means the path was removed, not merely restricted.

[Query Methods](/reference/methods) documents the four methods and their true return shapes.

## Errors at definition time

Three checks run while `defineResource` executes, so a misconfigured resource fails on boot instead of on the first request:

| Condition                                                            | Message                                                                 |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `query.pagination.modes` is empty                                    | `Resource "orders" must allow at least one pagination mode`             |
| The default mode is not in `modes`                                   | `Default pagination mode "offset" is not allowed for resource "orders"` |
| `modes` includes `"cursor"` and root `id` is missing or non-sortable | `Cursor pagination requires a visible, sortable root "id" field`        |

Everything else — unknown filter keys, disallowed sort keys, oversized requests — is checked per request. [Error Handling](/integration/error-handling) maps each failure to a status code.
