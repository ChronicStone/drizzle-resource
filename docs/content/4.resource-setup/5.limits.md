---
title: Request Limits
description: The six request limits and their defaults, the exact error each one throws, engine enforcement without a validator, and how requestSchema overrides can only lower them
---

Request limits are the upper bounds a resource enforces on every incoming request. They exist because a filter tree and a facet list are client-controlled, and both can be made expensive on purpose.

The engine checks them itself. A caller that skips the validator and calls `resource.query` directly is still bounded.

## The six limits

| Limit             | Default | What it measures                                   | Error                                          |
| ----------------- | ------- | -------------------------------------------------- | ---------------------------------------------- |
| `maxPageSize`     | `100`   | `pagination.pageSize`, after defaults are applied  | `Page size cannot exceed 100`                  |
| `maxCursorLength` | `2048`  | `pagination.cursor.length`, cursor mode only       | `Cursor cannot exceed 2048 characters`         |
| `maxFilterDepth`  | `5`     | Deepest nesting level of the merged filter tree    | `Filter tree cannot exceed 5 levels`           |
| `maxFilterNodes`  | `50`    | Total conditions **and** groups in the merged tree | `Filter tree cannot exceed 50 nodes`           |
| `maxFacetCount`   | `10`    | `request.facets.length`                            | `A request cannot contain more than 10 facets` |
| `maxFacetLimit`   | `50`    | Each individual `facet.limit`                      | `Facet limit cannot exceed 50`                 |

Top-level filter nodes sit at depth 1, so `maxFilterDepth: 5` permits four levels of nesting beneath them. Group nodes count against `maxFilterNodes` alongside conditions, which makes a deeply nested tree hit the node budget faster than a flat one.

`maxCursorLength` bounds an encoded payload that carries the resource key, the effective sorting, and one value per sort key. Long sort tuples and long text sort values both grow the cursor.

## Setting them on a resource

Declare the broadest bounds the resource can safely serve:

```ts twoslash
import { engine } from "./engine";
// ---cut-before---
export const ordersResource = engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    validation: {
      maxPageSize: 100,
      maxFilterDepth: 4,
      maxFilterNodes: 40,
      maxFacetCount: 6,
      maxFacetLimit: 25,
    },
  },
});
```

Unset keys fall back to the package defaults, so a partial `validation` object is fine.

Both the defaults and the resolved values are readable at runtime:

```ts twoslash
import { defaultQueryValidation } from "drizzle-resource";

import { ordersResource } from "./twoslash-support";
// ---cut-before---
const packageDefault: number = defaultQueryValidation.maxPageSize;
const resourceLimit: number = ordersResource.queryConfig.validation.maxPageSize;
```

`queryConfig.validation` is fully resolved — every key is present, with the resource value or the package default.

## Enforcement order

Each query method normalizes and checks the request in a fixed order:

::steps{level="3"}

### Merge the scope

`query.scope` runs and its nodes are prepended to `request.filters`.

### Normalize

Pagination, sorting, and search defaults are applied, and cursor mode appends the `id` tiebreaker.

### Check the limits

`maxPageSize`, `maxCursorLength`, the two filter budgets, and the two facet budgets are asserted.

### Check the fields

Pagination mode, sort keys, search fields, and filter keys are resolved against the registry.

::

Limits are checked **before** field names — a request that is both oversized and references an unknown filter key reports the size error first.

Every failure is a plain `Error` with no code attached. [Error Handling](/integration/error-handling) covers mapping them to status codes.

## Scope counts toward the filter limits

The scope is merged before the limits are asserted, so its nodes are part of the budget. A scope that wraps its conditions in `f.and([...])` also adds one level of depth to every client node beneath it.

Budget for it when you tighten `maxFilterNodes` or `maxFilterDepth`. A resource with a three-condition scope and `maxFilterDepth: 2` leaves the client no room to nest at all.

## Lowering a limit per endpoint

`requestSchema` accepts a `limits` override, and each value resolves to the lower of the resource limit and the override:

```ts twoslash
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource } from "./twoslash-support";
// ---cut-before---
const parsePublicRequest = requestSchema(ordersResource, {
  limits: { maxPageSize: 25, maxFacetCount: 3 },
});
```

An override above the resource value is ignored. A validator can only narrow what the resource already allows — see [Validation](/integration/validation).

## Where the limits stop

Three gaps are worth knowing before you rely on a limit as a guarantee:

- `maxFacetCount` and `maxFacetLimit` are asserted against `request.facets`. `queryFacets({ request, facets })` checks its `facets` argument against `facets.allowed` only, so cap that array yourself when it comes from a client.
- A facet with no `limit` is unbounded. Set a default limit at the transport layer if a field can have many distinct values.
- Page size bounds root rows, not hydrated rows. A page of 100 orders with a `many` relation can still return thousands of child rows — [Execution Cost](/performance/execution-cost) covers that shape.
