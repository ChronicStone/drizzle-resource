`drizzle-resource` ships as a single package with subpath exports for the validator integrations.

::code-group

```bash [npm]
npm install drizzle-resource
```

```bash [pnpm]
pnpm add drizzle-resource
```

```bash [bun]
bun add drizzle-resource
```

::

## Peer versions

| Peer          | Range           | Required                            |
| ------------- | --------------- | ----------------------------------- |
| `drizzle-orm` | `>= 1.0.0-rc.4` | Yes                                 |
| `zod`         | `^4.4.3`        | Only for `drizzle-resource/zod`     |
| `valibot`     | `^1.4.2`        | Only for `drizzle-resource/valibot` |

The relations API this library builds on landed in Drizzle 1.0. Earlier versions do not expose the relation graph the field registry needs.

::warning
Zod 3 does not work. The request schemas use `z.strictObject` and Zod 4 internals.
::

## What the engine needs

The engine takes three things, and all three come from your existing Drizzle setup:

::field-group
::field{name="db" type="DrizzleDatabase" required}
A Drizzle Postgres client created with both `schema` and `relations`. The engine uses `db.query.<table>.findMany` for row hydration and the query builder for the ids and facet stages.
::
::field{name="schema" type="Record<string, PgTable>" required}
Your table map — the same object you pass to `drizzle()`.
::
::field{name="relations" type="Relations" required}
The relation graph, built with `defineRelationsPart`. This is what turns `customer.name` into a resolvable field path.
::
::

A minimal setup looks like this:

::code-group

```ts [schema.ts]
import { pgTable, timestamp, uuid, varchar } from "drizzle-orm/pg-core";

export const customers = pgTable("customers", {
  id: uuid().defaultRandom().primaryKey(),
  name: varchar({ length: 255 }).notNull(),
  orgId: varchar({ length: 255 }).notNull(),
});

export const orders = pgTable("orders", {
  id: uuid().defaultRandom().primaryKey(),
  createdAt: timestamp({ withTimezone: true }).notNull(),
  customerId: uuid()
    .notNull()
    .references(() => customers.id),
  reference: varchar({ length: 255 }).notNull(),
  status: varchar({ length: 64 }).notNull(),
});

export const schema = { customers, orders };
```

```ts [relations.ts]
import { defineRelationsPart } from "drizzle-orm";

import { schema } from "./schema";

export const relations = defineRelationsPart(schema, ({ customers, orders, many, one }) => ({
  customers: {
    orders: many.orders({ from: customers.id, to: orders.customerId }),
  },
  orders: {
    customer: one.customers({
      from: orders.customerId,
      optional: false,
      to: customers.id,
    }),
  },
}));
```

```ts [db.ts]
import { drizzle } from "drizzle-orm/node-postgres";

import { relations } from "./relations";

export const db = drizzle(process.env.DATABASE_URL!, { relations });
```

::

Pass `relations` to `drizzle()`. Without it, `db.query` cannot hydrate the relations a resource declares.

::note
`drizzle()` takes `relations` only — `schema` is not part of its config in Drizzle 1.0. The engine receives `schema` separately, which is why `createQueryEngine` asks for all three.
::

## Cursor pagination requirement

Resources that enable cursor mode need a visible, sortable root `id` column. `defineResource` throws at startup if `id` is hidden or non-sortable, so a misconfiguration fails on boot rather than on the first request.

## TypeScript

Enable `strict` mode. Field-path inference relies on literal types, and without `strict` the path unions widen to `string` — which removes the compile-time checks that are the point of the library.

```json [tsconfig.json]
{
  "compilerOptions": {
    "strict": true
  }
}
```
