## Model field rules and views

Declare field rules on the engine. They apply to root rows and every occurrence of a model inside a relation.

- `private` fields never appear in resource rows or public query paths. Explicit selections are rejected. Trusted server scopes can still use them for access checks.
- `hidden` fields are omitted from default output and its inferred type. A view can explicitly select them. This is an output default, not authorization; existing query restrictions still govern public filtering and sorting.
- `virtual` fields are SQL expressions. They are opt-in for output and work through the existing filter, search, and sort configuration.

Use `ModelDefinitions` with `satisfies` to give nested virtual factories their owning table and database types without widening the registered field names. Alternatively, annotate the virtual factory parameters explicitly.

```ts twoslash
import { count, sql, sum } from "drizzle-orm";
import { createQueryEngine, virtual } from "drizzle-resource";
import type { ModelDefinitions } from "drizzle-resource";
import { db } from "./db";
import { schema } from "./schema";
import { relations } from "./relations";

const engine = createQueryEngine({
  db,
  schema,
  relations,
  models: {
    orders: { private: ["deletedAt"] },
    customers: {
      hidden: ["orgId"],
      virtual: {
        displayName: virtual.text((customer) => sql`upper(${customer.name})`),
      },
    },
  } satisfies ModelDefinitions<typeof schema, typeof db>,
}).withContext<{ orgId: string }>();

const orders = engine.defineResource("orders", {
  relations: { customer: true },
  views: {
    list: {
      select: {
        id: true,
        reference: true,
        totalAmount: true,
        customer: { select: { id: true, displayName: true } },
      },
    },
    internal: {
      select: {
        id: true,
        customer: { select: { id: true, name: true, orgId: true } },
      },
    },
  },
  query: {
    scope: (f, context) => f.is("customer.orgId", context.orgId),
    search: { allowed: ["reference", "customer.displayName"] },
  },
  summary: (order) => ({
    rows: count(),
    totalAmount: sum(order.totalAmount),
  }),
});

type ListRow = typeof orders.$infer.views.list;
type Summary = typeof orders.$infer.summary;

const result = await orders.query({
  context: { orgId: "acme" },
  view: "list",
  summary: true,
  request: {
    pagination: { pageIndex: 1, pageSize: 25 },
    filters: [],
    sorting: [],
    search: { value: "", fields: [] },
  },
});

result.summary.totalAmount;
//             ^?
```

A view's `select` is exact. A relation selected with `true` returns its target's default scalar fields without further relations or virtuals. A selected to-one relation keeps the nullability declared by Drizzle; selected to-many relations are arrays. Internal ordering IDs are removed when they are not selected.

View names are server-selected literal unions. They are supported by `query`, `findById`, `queryRows`, and `scan`. Existing `hydration.profiles` and `load` remain available; pass either `view` or `load`, never both. With neither, the existing hydration defaults apply together with model field policies. Choosing a view does not authorize the caller.

## Typed scalar virtuals

`virtual.scalar` embeds a typed one-column Drizzle query as a correlated scalar subquery. It preserves the selected value's decoder and adds `null` for a missing row. Multiple selected columns are rejected, and PostgreSQL rejects a scalar query returning multiple rows. It builds SQL rather than fetching each row separately.

```ts twoslash
import { desc, eq } from "drizzle-orm";
import { createQueryEngine, virtual } from "drizzle-resource";
import type { ModelDefinitions } from "drizzle-resource";
import { db } from "./db";
import { schema, orders } from "./schema";
import { relations } from "./relations";

const engine = createQueryEngine({
  db,
  schema,
  relations,
  models: {
    customers: {
      virtual: {
        latestOrderReference: virtual.scalar((customer, { db }) =>
          db
            .select({ value: orders.reference })
            .from(orders)
            .where(eq(orders.customerId, customer.id))
            .orderBy(desc(orders.createdAt), desc(orders.id))
            .limit(1),
        ),
      },
    },
  } satisfies ModelDefinitions<typeof schema, typeof db>,
});
```

Factories receive the owning table alias and the current execution database or transaction. Always use that table parameter for correlation. The `text`, `number`, `boolean`, and `timestamp` helpers specify runtime decoding. Wrap a nullable expression with `virtual.nullable(...)`. Do not use `virtual.number` for precise monetary values unless conversion to a JavaScript number is intentional.

## Summary semantics and cost

The summary callback returns a non-empty object of Drizzle aggregate expressions. It receives root columns and SQL virtuals, excluding private fields. There are no automatic aggregates through to-many paths in this iteration.

The engine applies the same mandatory scope, filters, and search as the row query, before aggregation. Page size, offset, cursor position, and sorting do not restrict the summary. Repeated matching children do not multiply the root rows being aggregated. An empty page can therefore have a non-empty summary.

All summary metrics run in one aggregate SQL statement, without hydrating or transferring the matching dataset. When an exact pagination count is requested, the statement also supplies the root count so the page does not run a separate count query. No summary runs unless requested, and `scan` does not compute summaries.

`querySummary({ request, context, db? })` returns just the inferred summary, using the same definition. This lets a client refresh its footer when filters change without recomputing it for every page.

Drizzle determines the aggregate result types and decoders. `count()` returns a number; `sum()` returns a decimal string or `null`. Empty sums are not silently converted to zero. Use an explicit SQL `coalesce` and decoder if the domain requires zero. Summary fields are an explicitly published output, independent of the row view; a hidden field can be deliberately aggregated.

Exact aggregation still requires database work proportional to the matching data and query plan. No latency bound is implied. The page and summary use separate statements; pass a repeatable-read transaction through `db` when both must observe the same snapshot. Summaries currently require the built-in query and ID strategies; a custom row hydration strategy remains supported.

## Runtime response validators

Zod and Valibot `responseSchema` accept `{ view: "list" }` and respect model privacy and hidden defaults. Scalar-query virtuals require an explicit column schema override because their TypeScript result type is erased at runtime. Built-in expression helpers supply their runtime value kinds.

For summary responses, provide `{ view: "list", summary: yourSummarySchema }`. Its output is checked against the inferred summary type. Arbitrary SQL expressions do not carry enough runtime metadata to derive validation rules automatically.
