---
title: Defining a Resource
description: The full structure of defineResource — relations, hydration, scope, search, sort, filters, facets, defaults, and strategies.
---

`engine.defineResource(root, options)` creates a resource bound to one root table. It is the primary configuration surface of the package.

```ts twoslash
// @noErrors
import { engine } from "./engine";

const ordersResource = engine.defineResource("orders", {
  relations: {},
  query: {},
  strategy: {}, // optional
});
```

## `root`

The table name as it appears in your schema map — for example `'orders'`, `'products'`, `'customers'`. This is the table the resource is built around.

## `relations`

The complete relation capability graph for the resource. It defines which nested field paths are valid and, when `hydration` is omitted, which relations are loaded by default.

```ts twoslash
// @noErrors
import { engine } from "./engine";

engine.defineResource("orders", {
  relations: {
    customer: true,
    orderLines: {
      with: {
        product: true,
      },
    },
  },
});
```

This does two things:

1. **Defines the available row shapes** — every hydration profile and inline override must be a subset of this tree.
2. **Registers nested field paths** — `customer.name`, `orderLines.product.name`, `orderLines.product.category.label` all become valid field paths for search, sort, filter, and facet configuration.

Filtering through a relation does not require returning it. The ids stage joins the paths needed by filtering, sorting, search, scope, and facets; row hydration independently uses the selected profile.

## `hydration`

Named relation subsets let each read operation load the shape it needs without duplicating the resource's scope or field policy.

```ts twoslash
// @noErrors
import { engine } from "./engine";

engine.defineResource("orders", {
  relations: {
    customer: true,
    orderLines: { with: { product: true } },
  },
  hydration: {
    profiles: {
      list: { customer: true },
      detail: {
        customer: true,
        orderLines: { with: { product: true } },
      },
      root: {},
    },
    defaults: {
      query: "list",
      findById: "detail",
    },
  },
});
```

`query()` and `queryRows()` use the `query` default. `findById()` uses the `findById` default. When a default is omitted, the complete `relations` tree remains the fallback.

Profiles and inline overrides are fully inferred:

```ts twoslash
import { ordersResource, request } from "./twoslash-support";

const detailPage = await ordersResource.query({
  request,
  context: { orgId: "acme" },
  load: "detail",
});

const customerOnly = await ordersResource.findById({
  id: "order_123",
  context: { orgId: "acme" },
  load: { customer: true },
});
```

An override replaces the configured default exactly; profiles are never merged implicitly. Profile selection is trusted server configuration and is not added to the client request schema.

## `query`

The declarative behavior of the resource. Everything in `query` can be left out — the engine falls back to reasonable defaults.

### `query.scope`

A function that merges additional filters into every request. Use this for tenancy constraints, authorization rules, and soft-delete conditions.

```ts twoslash
// @noErrors
import type { ExampleFilterBuilder } from "./twoslash-support";

const query = {
  scope: (f: ExampleFilterBuilder, ctx: { orgId: string }) =>
    f.and([f.is("customer.orgId", ctx.orgId)]),
};
```

The filter builder is already created for the resource and typed from its `relations`.

See [Scope](/resource-setup/scope) for details and multi-tenant examples.

### `query.search`

Which fields are searchable and what gets searched by default:

```ts twoslash
// @noErrors
import type { ExampleSearchConfig } from "./twoslash-support";

const query = {
  search: {
    allowed: ["reference", "customer.name", "orderLines.product.name"],
    defaults: ["reference", "customer.name"],
  },
} satisfies { search: ExampleSearchConfig };
```

`allowed` is the full set of valid search fields. `defaults` is what gets searched when the client sends `search.fields: []`. See [Query Contract → Search](/query-contract/search).

### `query.sort`

Default sort and disabled fields:

```ts twoslash
// @noErrors
import type { ExampleSortConfig } from "./twoslash-support";

const query = {
  sort: {
    defaults: [{ key: "createdAt", dir: "desc" }],
    disabled: ["orderLines.product.name"],
  },
} satisfies { sort: ExampleSortConfig };
```

`defaults` applies when the client sends an empty `sorting` array. `disabled` silently drops those keys if the client sends them. See [Query Contract → Sorting](/query-contract/sorting).

### `query.filters`

Fields the client cannot use in filter conditions:

```ts twoslash
// @noErrors
import type { ExampleFiltersConfig } from "./twoslash-support";

const query = {
  filters: {
    hidden: [],
    disabled: [],
  },
} satisfies { filters: ExampleFiltersConfig };
```

`hidden` removes fields from the registry so they cannot be used in any client-supplied operation. `disabled` prevents them from being used as filter keys specifically.

### `query.facets`

Which fields can be requested as facets:

```ts twoslash
// @noErrors
import type { ExampleFacetsConfig } from "./twoslash-support";

const query = {
  facets: {
    allowed: ["status", "customer.name", "orderLines.product.category.label"],
  },
} satisfies { facets: ExampleFacetsConfig };
```

A facet request with a key not in `allowed` is rejected. See [Query Contract → Facets](/query-contract/facets).

### `query.defaults`

Fallback pagination values used during validation and request normalization:

```ts twoslash
// @noErrors
import type { ExampleDefaultsConfig } from "./twoslash-support";

const query = {
  defaults: {
    pagination: { pageSize: 25 },
  },
} satisfies { defaults: ExampleDefaultsConfig };
```

## `strategy`

Optional imperative overrides for any stage of the pipeline. See [Strategies](/resource-setup/strategies).

```ts twoslash
// @noErrors
import { offsetPageInfo } from "./twoslash-support";

const strategy = {
  ids: async ({
    request,
    context,
    utils,
  }: {
    request: unknown;
    context: unknown;
    utils: unknown;
  }) => ({ ids: [], pageInfo: offsetPageInfo }),
  rows: async ({
    request,
    context,
    ids,
    utils,
  }: {
    request: unknown;
    context: unknown;
    ids: unknown[];
    utils: unknown;
  }) => ({ rows: [] }),
  facets: async ({
    request,
    context,
    facets,
    utils,
  }: {
    request: unknown;
    context: unknown;
    facets: unknown[];
    utils: unknown;
  }) => ({ facets: [] }),
  query: async ({
    request,
    context,
    utils,
  }: {
    request: unknown;
    context: unknown;
    utils: unknown;
  }) => ({ rows: [], pageInfo: offsetPageInfo }),
};
```

Only override a stage when you have a measured performance reason to do so. The automatic pipeline handles the vast majority of cases correctly.
