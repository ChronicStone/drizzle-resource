---
title: checkIndexes
description: "Find the sorts, scopes, searches and facets that no index serves, from the Drizzle schema or from the live database."
---

`checkIndexes` compares what your resources let a client ask for with the indexes of the tables behind them. It returns plain data: use it in a test, in CI, or print it with `formatIndexFindings`.

## Usage

```ts twoslash
import { formatIndexFindings } from "drizzle-resource";
import { engine, ordersResource } from "./twoslash-support";
// ---cut---
// Every resource defined on the engine. Reads the Drizzle schema, no database.
const findings = engine.checkIndexes();

// One resource.
const own = ordersResource.checkIndexes();

// Also reads the real indexes and table sizes from PostgreSQL.
const live = await engine.checkIndexes({ live: true });

console.log(formatIndexFindings(findings));
```

Without `live`, the call is synchronous and needs no connection. With `live: true`, it returns a promise and reads `pg_index` (btree and `pg_trgm` indexes) and `pg_class.reltuples`. It then uses the indexes that exist in the database instead of the ones in the Drizzle schema, so an index created by hand counts and an index only declared in the schema does not.

To keep a schema honest in CI, fail on errors:

```ts
import { expect, test } from "vitest";
import { engine } from "./engine";

test("sorts and scopes are indexed", () => {
  expect(engine.checkIndexes().filter((finding) => finding.level === "error")).toEqual([]);
});
```

## Output

Run on the example engine of these docs:

```text
error  orders  default sort createdAt desc, id desc has no index
               index("orders_created_at_id_idx").on(t.createdAt.desc(), t.id.desc())
warn   orders  sorting by customerId, reference, status, totalAmount has no index: each page reads and sorts every matching row. Index it, or add it to sort.disabled
               index("orders_customer_id_id_idx").on(t.customerId, t.id)
               index("orders_reference_id_idx").on(t.reference, t.id)
               index("orders_status_id_idx").on(t.status, t.id)
               index("orders_total_amount_id_idx").on(t.totalAmount, t.id)
warn   orders  sort customer.id, customer.name joins every row of orders first: disable it or copy id, name onto orders
warn   orders  scope customer.orgId goes through a join: put orgId on orders
warn   orders  facet orderLines.product.category counts through the to-many relation orderLines: every facet request joins all its rows, and the join column has no index
               index("order_lines_order_id_idx").on(t.orderId)
```

Each finding is an object:

| Field      | Meaning                                                                          |
| ---------- | -------------------------------------------------------------------------------- |
| `resource` | The root table key of the resource.                                              |
| `level`    | `"error"`, `"warn"` or `"info"`. Findings come back errors first.                |
| `rule`     | One of the rules below.                                                          |
| `message`  | What is wrong, in plain words.                                                   |
| `fields`   | The field paths involved.                                                        |
| `fix`      | When an index fixes it: `{ drizzle, sql }`, one statement per line when several. |

`formatIndexFindings` prints the Drizzle form under each message. The SQL form is `finding.fix.sql`.

## Rules

| Rule                      | Level | Live only | What it means                                                                                                 |
| ------------------------- | ----- | --------- | ------------------------------------------------------------------------------------------------------------- |
| `default-sort-unindexed`  | error | no        | The default sort, under the scope, has no index. A warning when an index only lacks the `id` tie-breaker.     |
| `mixed-direction-sort`    | warn  | no        | The default sort mixes `asc` and `desc`, and no index has exactly those directions (or all of them reversed). |
| `sort-unindexed`          | warn  | no        | Columns a client can sort by have no index. One finding lists them, with one index each.                      |
| `relation-sort`           | warn  | no        | Sorting by a related column joins every row first. An error when it is the default sort. No index fixes it.   |
| `scope-through-relation`  | warn  | no        | The scope filters on a related table: every query joins it. Put the column on the root table.                 |
| `many-to-many-facet`      | warn  | no        | A listed facet counts through a to-many relation. The fix indexes the join column when it has no index.       |
| `search-unindexed`        | warn  | yes       | A default search field on a large table has no `lower(column)` trigram index.                                 |
| `search-numbers`          | info  | no        | A searchable field is not text. It is cast to text row by row and no index can help.                          |
| `open-surface`            | info  | no        | `search.allowed` or `facets.allowed` is not set, so every field is searchable or facetable.                   |
| `exact-count-large-table` | info  | yes       | The default count is exact on a table of 1,000,000 rows or more.                                              |

## How an index is matched

The engine sorts by the request's sort, then by `id`, and filters by the scope. An index serves a sort when:

- Its first columns are the scope's equality columns (`filters.is("orgId", ...)`), in any order.
- The sort columns follow, in order, ending with the `id` that pages and cursors append.
- Every direction matches the sort, or every direction is the opposite: a btree is read backwards.
- Nulls sort where the engine sorts them: first on `desc`, last on `asc`. Drizzle's `.desc()` puts nulls last, so on a nullable column use `.desc().nullsFirst()`. The finding says so when that is the only difference.

If the scope has equalities the index does not start with (`deletedAt is null`, `status = 'open'`), PostgreSQL still reads the index in order and filters those rows one by one. That is a warning, not an error, and no fix is suggested: add the column to the index only if the filter is selective. An index that starts with none of the scope columns is still an error.

A partial index (`where`) counts when the scope states its condition: a scope with `deletedAt` null or empty, or an equality on a literal, satisfies `where deleted_at is null` or `where status = 'open'`. If the sort would be served only when every query meets the condition and the scope does not say so, the finding is a warning that `checkIndexes` cannot confirm the index is used. An index does not count when it is not a btree, or has an expression where the engine compares the plain column. The analysis stops at the first set of columns that is unique and cannot be null (the primary key, a composite primary key, a unique constraint or a unique index): nothing after it can tie. A unique column that allows null keeps the `id` tie-breaker, because rows with a null can tie.

Text filters ignore case, so a text scope column such as `orgId: text()` is compared as `lower(org_id)`. A plain index on `org_id` cannot serve that. Index `lower(org_id)`, or add the field to `filters.caseSensitive` and keep the plain index. The finding names both.

## What it does not check

- Filters and sorts that only a request can choose. Sort-by-one-column is checked for every sortable column, but a mixed sort such as `year desc, month asc` is only known when it is the default sort.
- Resources with a custom `strategy.query` or `strategy.ids`: their sorts and scope are yours. Search and facet findings still apply.
- Virtual fields. Their SQL cannot be compared with an index.
- Row counts, outside the live rules. A static check cannot tell a 200-row table from a 200-million-row one.

The scope function is called once with a placeholder context so its filters can be read. Only the conditions of that one call are analysed: a scope that branches on the context (an admin sees every tenant, a user sees one) is read on the placeholder's branch. Pass sample values with `checkIndexes({ context })` to analyse another branch, or when the function throws.

Resources are held weakly by the engine, so one defined per request and dropped does not accumulate in `engine.checkIndexes()`. Identical findings are reported once.

## Options

| Option       | Default                         | Meaning                                                                        |
| ------------ | ------------------------------- | ------------------------------------------------------------------------------ |
| `live`       | `false`                         | Read PostgreSQL. The call returns a promise.                                   |
| `db`         | the engine's `db`               | The database to read when `live` is true, for example a read replica.          |
| `context`    | placeholder                     | Context passed to `query.scope`. Values are never used in a query.             |
| `largeTable` | search 100,000, count 1,000,000 | Row counts above which `search-unindexed` and `exact-count-large-table` apply. |

A table PostgreSQL has never analysed reports no size, and the live size rules skip it.
