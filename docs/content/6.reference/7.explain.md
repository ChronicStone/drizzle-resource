---
title: explain
description: "Run EXPLAIN on the exact statements a request makes and read what is slow, with the numbers from the plan and a fix."
---

`resource.explain()` takes the same `request` and `context` as `query`, builds the statements the engine would run for it, and runs `EXPLAIN` on each. It returns plain data, and `formatExplain` prints it for the console. PostgreSQL only: any other database gets an error saying so.

## Usage

```ts twoslash
import { formatExplain } from "drizzle-resource";
import { ordersResource, request } from "./twoslash-support";
// ---cut---
// EXPLAIN only: nothing is executed.
const planned = await ordersResource.explain({ request, context: { orgId: "acme" } });

// EXPLAIN (ANALYZE, BUFFERS): the statements run for real, so timings and rows read are measured.
const measured = await ordersResource.explain({
  request,
  context: { orgId: "acme" },
  analyze: true,
});

console.log(formatExplain(measured));
```

With `analyze: true` the statements run one after the other inside a read-only transaction that is rolled back, so nothing is kept and a slow request costs you its real time once. Run it where that cost is acceptable: on a replica, or with a statement timeout set on the connection.

The options are the ones `query` takes: `request`, `context`, `db`, `execution`, plus `analyze` and `summary: true` to explain the summary too.

## Output

Two slow requests of the repository's benchmark (1,000,000 `consumption` rows, 20,000 accounts), measured with `analyze: true`:

```text
consumption · sort year desc, month desc · facets billed:exclude-self,month:exclude-self,year:exclude-self · offset · count exact
  ids     0.1 ms   index consumption_year_month_id_idx, 50 rows read
  facets  220 ms   3 facets (year, month, billed) share one GROUPING SETS statement, which PostgreSQL runs on one CPU while it reads 1,000,000 rows
                   fix: request fewer facets at once, or load each facet in its own request: a statement with one facet can use parallel workers

consumption · sort year desc, month desc · offset · count none
  ids    838 ms   page 15,000 skips 749,950 rows to return 50: PostgreSQL reads and discards every row before the page
                  fix: use cursor pagination (pagination: { mode: "cursor" }): it starts after the last row of the previous page, at any depth
```

A stage with no warning prints how it reads its data: `index consumption_year_month_id_idx, 50 rows read`. Without `analyze` the time is `-`, the numbers are the planner's estimates and are written `about N`.

## The report

```ts
type ExplainReport = {
  resource: string;
  shape: string; // the request shape, see onQuery
  shapeKey: RequestShape;
  analyzed: boolean;
  stages: ExplainStage[];
  planning: Array<{ stage: QueryStage; sql: string; ms: number; rows: number }>;
  notes: string[];
};

type ExplainStage = {
  stage: "ids" | "count" | "facets" | "summary";
  label?: string; // which facets a facets statement answers
  sql: string; // with $1 placeholders
  ms?: number; // analyze only: execution time
  rowsRead?: number; // analyze only: rows the scans looked at, including filtered-out ones
  rowsReturned?: number; // analyze only
  summary: string; // how the statement reads its data
  plan: ExplainPlanNode; // PostgreSQL's plan, as EXPLAIN (FORMAT JSON) prints it
  warnings: Array<{
    code: ExplainWarningCode;
    message: string;
    fix?: string;
    basis: "measured" | "estimated";
  }>;
  attempt?: "ordinary" | "indexed"; // see "A search without a count"
  budget?: { ms: number; exceeded: boolean }; // analyze only, on the ordinary attempt
};
```

- The statements are the engine's own. A test checks that, for every kind of request, the `sql` of each stage equals the `sql` of the `onQuery` event the same request produces.
- `planning` lists the statements the engine ran while choosing a search plan. They ran, whatever `analyze` says: they are small and bounded.
- A page's rows are a primary-key lookup of the ids and are not explained. A custom `strategy.ids` or `strategy.query` makes `explain` throw, and a `strategy.facets` is left out with a note: those statements are yours.
- An `estimated` count is not a statement: it is the planner's row estimate for the page's filters. Its `count` stage shows that plan, with a `label` saying so. A `capped` count is explained as a count that stops at the cap.
- With a `capped` or `estimated` count and `facets.whenCapped: "skip"`, facets are explained as if the count were under the cap, and a note says so.
- The plan holds the values of the request in its filters. Do not ship a report to a log service the way you ship a shape.

## A search without a count

A search that has no exact count runs its first statement on the ordinary plan with a time budget (`search.planBudget`, 25 ms by default). A common term finishes within it. A rare term makes PostgreSQL walk the whole sort index, runs out of budget and is retried with the indexed plan. `explain` shows both attempts, as two stages marked `attempt: "ordinary"` and `attempt: "indexed"`:

- Without `analyze`, both statements are explained, and a note gives the planner's cost of each. The engine cannot know which one a request will use before it runs.
- With `analyze`, the ordinary attempt runs under the same budget, inside the same rolled-back transaction. If it finishes in time, only that stage is reported and a note says the indexed plan is never used. If it runs over, the stage says so (`budget.exceeded`, shown as `stopped at its 25 ms budget`), the indexed plan is run and measured as the second stage, and a note says every request with this search pays the budget first.
- Inside a transaction you pass as `db`, the engine applies no budget, and neither does `explain`: there is one stage.

## Text filters

A text filter compiles to `lower(column) = $1`, and a text search to `lower(column) LIKE '%value%'`. A plain index on `column` serves neither. When a warning comes from such a filter, its fix names the expression:

```text
fix: index the expression lower(status) (CREATE INDEX ON orders (lower(status))): the engine compares text without case, so a plain index on status is not used. Or add "status" to filters.caseSensitive and keep the plain index
```

PostgreSQL gathers no statistics on `lower(status)` until an index or extended statistics cover the expression, so for a `misestimate` on such a filter the fix is an expression index or `CREATE STATISTICS ... ON (lower(status))`, not `ANALYZE` alone.

## Warnings

| Code                | Fires when                                                                                                                                                        | Fix                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `full-count`        | An exact count reads 100,000 rows or more and counts more than `countCap` of them. It is also reported on the facets or summary statement that carries the count. | `count: "capped"`                                                      |
| `index-walk`        | A sort index is read row by row under a `LIMIT` while a filter drops 10 times more rows than it keeps, and at least 10,000 rows.                                  | An index that starts with the filtered columns and ends with the sort. |
| `seq-scan`          | A filter keeps less than 10% of a table of 100,000 rows or more and no index serves it.                                                                           | An index on the filtered columns.                                      |
| `deep-offset`       | An offset page skips 10,000 rows or more.                                                                                                                         | Cursor pagination.                                                     |
| `misestimate`       | `analyze` only: a node returned 10 times more or fewer rows than planned, a difference of at least 10,000 rows.                                                   | `ANALYZE`, then extended statistics.                                   |
| `relation-sort`     | The sort is on a related table's column: every row joins before it can sort, and at least 100,000 rows do.                                                        | Copy the column onto the root table, or disable the sort.              |
| `single-cpu-facets` | Several facets share one `GROUPING SETS` statement that reads 100,000 rows or more. PostgreSQL does not parallelise it.                                           | Lower `query.facets.splitAbove`: above it each facet runs on its own.  |

A walk that the planner chose because it believed most rows match is invisible before the statement runs: without `analyze`, `index-walk` fires only when the planner itself expects the long walk. When a walk runs far longer than planned, `misestimate` reports what the rows it walked imply.

The limits are in `explainThresholds` of the source and are the same for every resource.
