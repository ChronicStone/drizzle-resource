Understanding what SQL the engine runs helps you know where to look when performance is not where you want it.

## The four stages

```
request
  ↓
1. Normalize & validate   — apply defaults, merge scope, validate field paths
  ↓
2. Ids query              — SELECT the current id page, optionally COUNT(*)
  ↓
3. Rows query             — db.query.root.findMany({ with: relations })
  ↓
4. Facets (if requested)  — grouped aggregates, batched on PostgreSQL when compatible
  ↓
response: { rows, pageInfo, facets? }
```

Only the ids and rows stages are mandatory. Facets are skipped entirely if `request.facets` is empty or absent.

These are logical stages. In the default pipeline, requested facets are computed before the IDs so a compatible aggregate can also supply the exact count. Custom strategies retain control of their own execution.

## Stage 1 — Normalize & validate

No database work. The engine:

- merges `query.scope` filters into the request's top-level filter array
- applies `sort.defaults` if `sorting` is empty
- applies `search.defaults` if `search.fields` is empty
- applies `defaults.pagination.pageSize` if not set
- validates every field path (sort keys, filter keys, search fields, facet keys) against the resource's registry

Validation errors surface here before any SQL runs.

## Stage 2 — Ids query

This is where the engine selects the page of matching row ids. An exact count only runs when `pagination.count` is `"exact"`; it is a separate query unless a compatible facet aggregate already supplied it.

On PostgreSQL, the engine reads primary keys, unique constraints, and non-partial unique indexes from the Drizzle schema. When the root ID is unique and every joined target is unique on its join columns, the engine selects the page directly:

```sql
SELECT orders.id
FROM orders
INNER JOIN customers ON orders.customer_id = customers.id
WHERE [scope + client filters + search conditions]
ORDER BY [sorting]
LIMIT [pageSize] OFFSET [(pageIndex - 1) * pageSize]
```

Cursor mode replaces the offset with a lexicographic boundary over the effective sorting and fetches one extra id to determine whether another page exists. When `count: "none"`, this avoids both the exact count and the deep offset.

An exact count uses `count(*)` over the same filters and joins. It still scans the complete filtered result. When uniqueness cannot be proven, the engine keeps the distinct matching-ID path; a declared `one` relation alone is not a uniqueness guarantee. Other SQL dialects retain that general path.

Count and facet aggregation keep sorting-only relations out of their outer joins. An existence predicate preserves the original inner-join membership, including missing optional relations, without multiplying aggregate rows. When a requested facet group has exactly the page count's predicates and join paths, PostgreSQL adds an empty grouping set to compute the exact total in that same aggregate. Different exclude-self filters or relation membership keep a separate count.

For whole-selection exports, [Bulk Scans](/performance/bulk-scans) use one PostgreSQL cursor execution instead of restarting page selection.

**This stage is the most impactful to optimize.** Relation-heavy ORDER BY clauses, many-to-many joins for search or filters, and large OFFSET values all accumulate cost here.

## Stage 3 — Rows query

Once the engine has the ordered id list from stage 2, it hydrates the full row objects:

```ts twoslash
// @noErrors
import { ids, orders } from "./twoslash-support";
import { db, inArray } from "./twoslash-support";

db.query.orders.findMany({
  where: inArray(orders.id, ids),
  with: {
    customer: true,
    orderLines: { with: { product: true } },
  },
});
```

Drizzle fetches exactly the rows you asked for and joins the selected hydration profile. Keep list profiles narrow; detail profiles can load the broader graph because they hydrate one known row.

The engine then restores the order from the ids array, since `inArray` does not guarantee order.

## Stage 4 — Facets

Facets aggregate directly over the filtered root and the joins needed for their values. They do not materialize all matching IDs and join the root table again:

```sql
-- Example: facet on status
SELECT
  orders.status AS value,
  count(*) AS count
FROM orders
INNER JOIN customers ON orders.customer_id = customers.id
WHERE [same scope + client filters, minus self if exclude-self]
GROUP BY orders.status
ORDER BY count DESC
LIMIT [facet.limit]
```

The count is `count(*)` only when schema constraints prove the joins cannot multiply roots; otherwise it is `count(distinct orders.id)`. A window count over the buckets supplies `total` in the same statement, and SQL applies each facet's limit and cursor before sending buckets to the application.

On PostgreSQL, compatible facets share a `GROUPING SETS` aggregate. Compatibility requires equal filter SQL and bound values, the same join paths, proven root cardinality, and no facet-specific value search. Different filter universes, many-relations, duplicate fields, and value searches retain independent aggregates. Native column decoders preserve boolean, numeric, and other facet value types.

`exclude-self` removes matching client filters only. The server's `query.scope` always remains in every facet query, including a facet on the scope field itself.

Facets share the filter universe with the main query but run independently from stages 2 and 3. The cost scales with:

- the number of incompatible facet groups (each needs a separate query)
- the join complexity of each facet's field path
- the cardinality of the grouped field (high-cardinality fields like `customer.email` are expensive to aggregate)

## Where cost accumulates

| Scenario                   | Main cost driver                    | Where to look                                   |
| -------------------------- | ----------------------------------- | ----------------------------------------------- |
| Large table, no relations  | OFFSET for deep pages, count query  | `strategy.ids` with keyset pagination           |
| Relation-heavy sort/filter | JOIN in ids query                   | `strategy.ids` with simpler join shape          |
| Many-to-many search        | Subquery for each ILIKE on m2m path | `search.defaults` — remove m2m paths            |
| Multiple facets            | Scans per compatible facet group    | Review join paths and grouped-field cardinality |
| m2m facet path             | `count(distinct)` + junction join   | `strategy.facets` or remove from `allowed`      |

## The impact of good database indexes

Before adding custom strategies, ensure your database has indexes on:

- Foreign key columns used in JOIN conditions (`orders.customer_id`, `order_lines.order_id`)
- Columns used in WHERE conditions from common filters (`orders.status`, `orders.created_at`)
- Columns used in ORDER BY (`orders.created_at`, `customers.name`)

Good indexes can reduce the ids query from hundreds of milliseconds to single digits. See [Benchmark Results](/performance/benchmarks) for measured before/after data.

## Retained memory

The engine retains schema-derived metadata through weak references. It does not retain a growing cache of arbitrary filter-field or sorting combinations. Database memory still depends on concurrent query plans, grouping cardinality, the connection pool, and PostgreSQL's memory settings; the automatic optimizations do not raise pool size or `work_mem`.
