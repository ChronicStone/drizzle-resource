---
title: Bulk Scans
description: Export an entire scoped selection through bounded batches, using one PostgreSQL cursor execution with automatic cleanup.
---

Use `resource.scan(options, consume)` when every matching row is needed, such as an Excel export or a background data-processing job. Normal pagination selects a new page each time. On PostgreSQL, a scan opens one ordered selection and resumes that execution with bounded cursor fetches.

## Consume typed batches

```ts twoslash
import { ordersResource, request } from "./twoslash-support";

const exportedRows = await ordersResource.scan(
  {
    request,
    context: { orgId: "acme" },
    batchSize: 1000,
    count: "exact",
    load: "detail",
  },
  async (batches) => {
    let processed = 0;
    for await (const { rows, totalRows } of batches) {
      processed += rows.length;
      console.log({ processed, totalRows });
    }
    return processed;
  },
);
```

The callback receives `AsyncIterable<{ rows, totalRows? }>` and its return value becomes the scan's return value. An existing export writer that accepts async pages can consume this iterable directly inside the callback. Rows infer the resource's default query hydration or the selected `load` profile, exactly as with `query`.

`request` is optional and accepts filters, sorting, and search. Passing an existing table request reuses those fields but ignores its pagination and facets: a scan always visits the full matching selection and never computes sidebar facets. Scope and validation run once, and a unique ID tie-breaker preserves deterministic ordering.

`batchSize` defaults to 1,000 and must be a positive safe integer. It is a trusted server-side option, independent of the public page-size limit. Do not bind it directly to untrusted request input. Await your writer inside the loop before requesting another batch. The engine does not fetch ahead or collect all IDs or rows in JavaScript memory.

`count` defaults to `"none"`. With `"exact"`, PostgreSQL computes the total once in the cursor selection, and every emitted batch carries `totalRows`. An empty selection emits no batches. The exact total can require processing and buffering the entire selection before the first batch; leave it disabled when progress only needs a processed-row count.

## Snapshot and connection ownership

PostgreSQL scans use `DECLARE ... NO SCROLL CURSOR`, `FETCH`, and `CLOSE` inside a repeatable-read, read-only transaction. The selection and hydrated relations see the same snapshot, so concurrent inserts, deletes, and updates do not move rows between batches or change exported values midway through the scan.

One connection and snapshot remain open for the entire callback. Keep export concurrency bounded and avoid unrelated uploads or long waits inside it. PostgreSQL still performs the selection's real filtering, joining, sorting, and optional count work; the cursor avoids restarting that work for every page. Sorts and exact totals may use database temporary storage. A scan is not a resumable export checkpoint.

The engine closes the cursor on normal completion, `break`, callback failure, and cancellation. The iterator cannot be used after the callback returns. `signal` accepts an `AbortSignal`; cancellation is checked between database operations and before completing the callback. It does not interrupt an already-running database statement, so configure driver/database statement timeouts for that limit.

Pass an existing repeatable-read or serializable transaction through `db` to share the export runtime's snapshot. The engine does not commit or roll back a caller-owned transaction. A read-committed transaction is rejected rather than silently providing inconsistent hydration.

```ts twoslash
import { drizzle } from "drizzle-orm/node-postgres";
import { relations, ordersResource, request } from "./twoslash-support";

const db = drizzle({ connection: { database: "app" }, relations });

await db.transaction(
  async (transaction) => {
    await ordersResource.scan(
      { request, db: transaction, context: { orgId: "acme" } },
      async (batches) => {
        for await (const { rows } of batches) {
          console.log(rows.length);
        }
      },
    );
  },
  { isolationLevel: "repeatable read", accessMode: "read only" },
);
```

## Portable behavior and custom strategies

The public interface is database-neutral. Native PostgreSQL optimization requires a Drizzle asynchronous PostgreSQL driver that supports interactive transactions and SQL cursors. HTTP-only drivers without interactive transactions cannot use this path.

Resources with custom `strategy.query` or `strategy.ids`, and non-PostgreSQL databases, use bounded pagination instead. The scope is still resolved once, facets are omitted, and an exact count is requested only for the first page. Custom row-hydration strategies also work with the PostgreSQL cursor path. Portable pagination does not promise the single-selection execution or snapshot consistency of the PostgreSQL path; those depend on the driver and strategy.

The native PostgreSQL path requires a unique, non-null root ID and provably unique relation keys for sorting. Multiplying filter joins are deduplicated before scanning. Ambiguous sorting relations are rejected instead of exporting duplicate roots.
