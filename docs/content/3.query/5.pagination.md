---
title: Pagination
description: Offset pages for numbered navigation, cursor pages for feeds and exports, and exact, capped, estimated or no counts.
---

Pagination has two modes. Offset mode supports numbered pages. Cursor mode moves forward through a result without the cost of large offsets.

| Mode     | Request                               | Counts by default | Good for                                     |
| -------- | ------------------------------------- | ----------------- | -------------------------------------------- |
| `offset` | `pageIndex` (starts at 1), `pageSize` | `"exact"`         | numbered pages, "page 4 of 12"               |
| `cursor` | `cursor` from the previous page       | `"none"`          | feeds, "load more", infinite scroll, exports |

## Offset

```ts twoslash
import type { QueryRequest } from "drizzle-resource";

const pagination: QueryRequest["pagination"] = {
  mode: "offset",
  pageIndex: 1,
  pageSize: 25,
  count: "exact",
};
```

Page 1 is offset 0; page 500 with 25 rows per page is offset 12,475. The response repeats the mode:

```ts twoslash
import type { QueryOffsetPageInfo } from "drizzle-resource";

const pageInfo: QueryOffsetPageInfo = {
  mode: "offset",
  pageIndex: 1,
  pageSize: 25,
  hasNextPage: true,
  count: "exact",
  rowCount: 12_483,
};
```

Change `pageIndex` in the example below to move through the sample data.

::live-query{title="Page 3, five rows per page" :request='{"pagination":{"mode":"offset","pageIndex":3,"pageSize":5,"count":"exact"},"sorting":[{"key":"createdAt","dir":"desc"}]}' :show='["rows", "sql"]'}
::

## Cursor

Allow cursor mode on the resource, and make it the default if you like:

```ts twoslash
// ---cut-start---
import type { ResourceQueryConfig } from "drizzle-resource";
type ExampleQueryConfig = Pick<
  ResourceQueryConfig<any, any, any, any, any, any>,
  "pagination" | "defaults" | "sort"
>;
// ---cut-end---
const query = {
  pagination: { modes: ["cursor", "offset"] },
  defaults: {
    pagination: { mode: "cursor", pageSize: 25 },
  },
  sort: {
    defaults: [{ key: "createdAt", dir: "desc" }],
  },
} satisfies ExampleQueryConfig;
```

The first request has no cursor. Each next request sends the `nextCursor` of the previous response:

```ts twoslash
import type { QueryRequestInput } from "drizzle-resource";

const firstPage: QueryRequestInput["pagination"] = {
  mode: "cursor",
  pageSize: 25,
};

const nextPage: QueryRequestInput["pagination"] = {
  mode: "cursor",
  cursor: "opaque-cursor-from-the-previous-response",
  pageSize: 25,
};
```

Cursor mode needs a visible, sortable root `id`:

- The engine appends it to the sort when missing, so `createdAt desc` becomes `createdAt desc, id desc` and equal timestamps keep a stable order.
- It fetches one extra id to know whether there's a next page. That row isn't returned.

```ts twoslash
import type { QueryCursorPageInfo } from "drizzle-resource";

const pageInfo: QueryCursorPageInfo = {
  mode: "cursor",
  pageSize: 25,
  nextCursor: "opaque-next-cursor",
  count: "none",
  rowCount: null,
};
```

A cursor is a position in one ordered result. Reset it to `null` when the sorting, filters, search or scope change.

## Counts

A count tells the interface how many rows match. Each request chooses how much it pays for that answer with `count`:

| `count`       | Reads                                       | `pageInfo`               | Good for                                   |
| ------------- | ------------------------------------------- | ------------------------ | ------------------------------------------ |
| `"exact"`     | every matching row                          | `rowCount`               | "page 4 of 12" on small and medium results |
| `"capped"`    | at most `countCap` rows (10,000 by default) | `rowCount`, `exact`      | "10,000+" on big tables                    |
| `"estimated"` | nothing: PostgreSQL's row estimate          | `rowCount` (approximate) | "about 8.5M" when a rough size is enough   |
| `"none"`      | nothing                                     | `rowCount: null`         | feeds, "load more", exports                |

Offset mode defaults to `"exact"` and cursor mode to `"none"`. Capped and estimated counts are opt-in: set them per request or as the resource default.

```ts twoslash
import type { QueryRequestInput } from "drizzle-resource";

const pagination: QueryRequestInput["pagination"] = {
  mode: "offset",
  pageIndex: 1,
  pageSize: 25,
  count: "capped",
};
```

`pageInfo.count` tells TypeScript which fields exist, and it reports the count that was actually used:

```ts twoslash
import type { QueryPageInfo } from "drizzle-resource";

declare function show(text: string): void;
declare const pageInfo: QueryPageInfo;

switch (pageInfo.count) {
  case "exact":
    show(`${pageInfo.rowCount} rows`);
    break;
  case "capped":
    show(pageInfo.exact ? `${pageInfo.rowCount} rows` : `${pageInfo.rowCount}+ rows`);
    break;
  case "estimated":
    show(`about ${pageInfo.rowCount} rows`);
    break;
  case "none":
    // `reason` is "timeout" when a requested count was dropped (see Timeouts).
    show(pageInfo.reason === "timeout" ? "count unavailable" : "");
    break;
}
```

### Capped counts

A capped count reads at most `countCap + 1` matching rows. Set the cap on the resource: it is never part of the request.

```ts twoslash
// ---cut-start---
import type { ResourceQueryConfig } from "drizzle-resource";
type ExampleQueryConfig = Pick<
  ResourceQueryConfig<any, any, any, any, any, any>,
  "pagination" | "defaults"
>;
// ---cut-end---
const query = {
  pagination: { modes: ["offset"], countCap: 10_000 },
  defaults: { pagination: { mode: "offset", count: "capped" } },
} satisfies ExampleQueryConfig;
```

When fewer rows match than the cap, `rowCount` is the true count and `exact` is `true`. When the cap is hit, `rowCount` equals the cap and `exact` is `false`.

```ts twoslash
import type { QueryOffsetPageInfo } from "drizzle-resource";

const pageInfo: QueryOffsetPageInfo = {
  mode: "offset",
  pageIndex: 1,
  pageSize: 25,
  hasNextPage: true,
  count: "capped",
  rowCount: 10_000,
  exact: false,
};
```

### Estimated counts

An estimated count reads the row estimate from PostgreSQL's planner. The estimate can be far off, so the engine uses it only when it is trustworthy and falls back to a capped count otherwise: filters or search through relations, virtual fields, an estimate at or below the cap, or a database that isn't PostgreSQL. Read `pageInfo.count` to see which one you got.

### Next pages without an exact count

An exact count tells offset mode whether a next page exists. In every other mode the engine fetches one extra id and reports `hasNextPage` from it, so `hasNextPage` stays correct when the count is capped, estimated or missing. Cursor mode always works this way.

### Counts in cursor mode

Cursor mode skips the count by default. Ask for one when the interface shows a total:

```ts twoslash
import type { QueryRequestInput } from "drizzle-resource";

const pagination: QueryRequestInput["pagination"] = {
  mode: "cursor",
  cursor: null,
  pageSize: 25,
  count: "capped",
};
```

Either mode accepts every count mode: an offset "load more" endpoint can skip the count too.

## Limits

```ts twoslash
// ---cut-start---
import type { ResourceQueryValidationConfig } from "drizzle-resource";
// ---cut-end---
const validation = {
  maxPageSize: 100,
  maxPageIndex: 400,
  maxCursorLength: 1024,
} satisfies ResourceQueryValidationConfig;
```

- `maxPageSize` applies to both modes.
- `maxPageIndex` is the highest offset page a client can request (unlimited by default). Offset 12,475 costs a lot more than offset 0, so cap it where a user can't reasonably go deeper.
- `maxCursorLength` defaults to 2,048 characters.

Direct calls and the Zod, Valibot and Vine request schemas all enforce these limits. An override on a request schema can only lower them.

Cursor pages can't jump to page 500 or show a page count without an exact total. Keep offset mode for numbered navigation.

## Timeouts

A resource can bound the statements behind a request. Each stage is set in milliseconds and applied with `SET LOCAL statement_timeout` inside a transaction, only for stages you configure:

```ts twoslash
// ---cut-start---
import type { ResourceQueryTimeoutsConfig } from "drizzle-resource";
// ---cut-end---
const timeouts = {
  count: 500,
  facets: 2_000,
  summary: 2_000,
} satisfies ResourceQueryTimeoutsConfig;
```

A stage that runs out of time degrades instead of failing the request, and the response says so:

| Stage     | When it times out                                                                                         |
| --------- | --------------------------------------------------------------------------------------------------------- |
| `count`   | `pageInfo` is `{ count: "none", rowCount: null, reason: "timeout" }`; the page still comes back.          |
| `facets`  | The affected facets come back with `status: "timeout"` and no options; the others are unchanged.          |
| `summary` | The response has `summaryStatus: "timeout"` and every summary value is `null`; the page still comes back. |

Where the timeout lives:

- **Pooled connections** (the default): each timed statement runs in a short transaction of its own, so facets still run in parallel. A request with `timeouts.facets` set can hold one connection per facet statement (one per `GROUPING SETS` group, or one per facet when facets are split above `facets.splitAbove`, and one per `missing` count) at the same time. Leave `timeouts.facets` unset on a small pool, or raise the pool size.
- **Your own transaction (`db: tx`):** the engine sets **no** timeout. Statements that overlap on one connection would share the limit, and a timeout would abort your transaction. The stages run untimed and no stage ever reports a timeout. Set `statement_timeout` on the transaction yourself if you want one.
- A stage is reported as timed out when PostgreSQL cancelled its statement and the statement had run for at least the timeout. A cancel from somewhere else (`pg_cancel_backend`, a client abort) and every other error are thrown. The check does not read the error message, so it works whatever `lc_messages` the server uses.
