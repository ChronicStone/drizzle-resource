title: Search
description: One search value matched across the fields you allow, relations included.

Search matches one value against one or more fields, case-insensitively, as a substring. A row matches when any of the searched fields contains the value.

```ts twoslash
// @noErrors
type SearchPayload = {
  // ---cut---
  search: {
    value: string; // the text to look for
    fields: string[]; // [] searches the resource's default fields
  };
};
```

The value is trimmed first. An empty value, or one made only of spaces, adds no condition.

## Which fields are searched

| The request sends    | Fields searched                                                             |
| -------------------- | --------------------------------------------------------------------------- |
| `fields: []`         | The resource's `search.defaults`.                                           |
| `fields: ["…", "…"]` | Those fields. Each must be in `search.allowed`, or the request is rejected. |

```ts twoslash
// @noErrors
import type { ExampleSearchConfig } from "./twoslash-support";

const queryConfig = {
  // ---cut---
  search: {
    allowed: ["reference", "customer.name", "orderLines.product.name", "orderLines.product.sku"],
    defaults: ["reference", "customer.name"],
  },
} satisfies { search: ExampleSearchConfig };
```

`allowed` is everything a client may opt into. `defaults` is what most users want searched. Without `allowed`, every field path is searchable.

## The SQL

Each field becomes `lower(column) LIKE '%value%'`, and the fields are combined with `OR`. A field on a relation is checked inside `EXISTS`, so a missing optional relation can't hide a row that matches another field:

```sql
WHERE (
  lower(orders.reference) LIKE '%laptop%'
  OR EXISTS (
    SELECT 1 FROM customers
    WHERE customers.id = orders.customer_id
      AND lower(customers.name) LIKE '%laptop%'
  )
)
-- combined with the scope and the filters with AND
```

On PostgreSQL, a selective search over `pg_trgm`-indexed text fields of several tables can use a cheaper plan that looks the matches up in the indexes first. How the engine chooses depends on the count:

| `count`                                                       | How the plan is chosen                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"exact"`                                                     | Both plans are priced with `EXPLAIN` and the cheaper one runs. Two extra planning statements, no extra work on the data.                                                                                                                                                                                                                                                                     |
| `"none"`, `"capped"`, `"estimated"` (engine-owned connection) | The ordinary plan runs first with a time budget. If it finishes in time, nothing else happens and the cost is the cost of the ordinary plan. If it doesn't, the engine retries that statement with the indexed plan under a budget four times larger. If that also runs out, the statement goes back to the ordinary plan with no budget. The count and the page each decide for themselves. |

Without an exact count, `EXPLAIN` can't tell a rare term from a common one, so a rare term would make PostgreSQL read the whole sort index. The time budget catches that case. It is `search.planBudget`, 25 ms by default:

```ts twoslash
// ---cut-start---
import type { ResourceQuerySearchConfig } from "drizzle-resource";
// ---cut-end---
const search = {
  allowed: ["reference", "customer.name"],
  planBudget: 25,
} satisfies ResourceQuerySearchConfig<"reference" | "customer.name">;
```

Each budgeted statement of a request, the count and the page, makes its own choice in up to three attempts. A capped count stops at its cap, so its plan says nothing about the page behind it, which still has to sort every match. What the count's _result_ says is used, though: see below.

1. The ordinary plan runs with `planBudget` (25 ms by default).
2. If it misses, the indexed plan runs with four times that budget.
3. If that misses too, the ordinary plan runs with no budget.

The worst case for one statement is the first budget, plus the second, plus the ordinary plan's time. It is never the indexed plan's full cost on a common term. A request with a count and a page can pay that for each of the two statements.

With a `"capped"` count the page starts from what the count found:

- **The count came back under its cap.** It is exact and small, so the page starts at the second attempt and runs the indexed plan, which reads at most that many matches. A rare term pays the first budget once, in the count.
- **The count hit its cap.** The matches are common, so the page starts at the first attempt, on the ordinary plan.
- **`"estimated"` over a search across tables.** PostgreSQL has no row estimate through a relation, so `"estimated"` falls back to `"capped"` and the page is steered the same way. (`pageInfo.count` says `"capped"`.)
- **`"none"`, or a count that timed out.** There is no count value to read, so the page makes all three attempts.

What it costs:

- **A common term** pays nothing beyond a transaction that sets the timeout, about one extra millisecond of round trips on a local database, per statement.
- **A rare term** pays the first budget once, in the count, plus two indexed queries (count, page) of a few milliseconds each, against hundreds for one walk of the sort index. Without a count it pays the budget once, for the page.
- **A busy server** can make a common term miss the first budget by accident. The retry on the indexed plan is bounded by the second budget, and the third attempt returns to the plan that is right for a common term.
- **A term in between** whose ordinary plan needs longer than the budget pays the budget and then the indexed query, which can be slower than letting the ordinary plan finish. Raise `planBudget` when your typical ordinary page takes longer than 25 ms.
- The budget never exceeds a `statement_timeout` already in force on the connection. When that timeout is below `planBudget`, every attempt is cut to it: a statement that needs longer runs the ordinary plan for the timeout, the indexed plan for the timeout, and the ordinary plan again with no budget under the same timeout, which the connection then cancels. The request fails with the same cancel error (SQLSTATE 57014) after the three attempts, not after the first. A smaller `timeouts.count` cuts the count's attempts short and the count degrades, but the page still makes its own three attempts.
- Inside your own transaction (`db: tx`) there is no budget. The engine prices both plans with `EXPLAIN`, as it does for an exact count, because a timeout there would apply to every statement running on the same connection.

[Indexes](/scale/indexes#search) shows which trigram indexes to create.

Keep `defaults` short: every default field adds a condition to every search, and many-to-many paths add a subquery each.
