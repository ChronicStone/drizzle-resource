title: Search
description: One search value matched across the fields you allow, relations included.

Search matches one value against one or more fields, case-insensitively, as a substring. A row matches when any of the searched fields contains the value.

```ts twoslash
// @noErrors
type SearchPayload = {
  // ---cut---
  search: {
    value: string; // the text to look for
    fields: string[]; // [] searches the resource's default fields
  };
};
```

The value is trimmed first. An empty value, or one made only of spaces, adds no condition.

## Which fields are searched

| The request sends    | Fields searched                                                             |
| -------------------- | --------------------------------------------------------------------------- |
| `fields: []`         | The resource's `search.defaults`.                                           |
| `fields: ["…", "…"]` | Those fields. Each must be in `search.allowed`, or the request is rejected. |

```ts twoslash
// @noErrors
import type { ExampleSearchConfig } from "./twoslash-support";

const queryConfig = {
  // ---cut---
  search: {
    allowed: ["reference", "customer.name", "orderLines.product.name", "orderLines.product.sku"],
    defaults: ["reference", "customer.name"],
  },
} satisfies { search: ExampleSearchConfig };
```

`allowed` is everything a client may opt into. `defaults` is what most users want searched. Without `allowed`, every field path is searchable.

## The SQL

Each field becomes `lower(column) LIKE '%value%'`, and the fields are combined with `OR`. A field on a relation is checked inside `EXISTS`, so a missing optional relation can't hide a row that matches another field:

```sql
WHERE (
  lower(orders.reference) LIKE '%laptop%'
  OR EXISTS (
    SELECT 1 FROM customers
    WHERE customers.id = orders.customer_id
      AND lower(customers.name) LIKE '%laptop%'
  )
)
-- combined with the scope and the filters with AND
```

On PostgreSQL, a selective search over `pg_trgm`-indexed text fields of several tables can use a cheaper plan that looks the matches up in the indexes first. How the engine chooses depends on the count:

| `count`                                                       | How the plan is chosen                                                                                                                                                                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `"exact"`                                                     | Both plans are priced with `EXPLAIN` and the cheaper one runs. Two extra planning statements, no extra work on the data.                                                                                                                                |
| `"none"`, `"capped"`, `"estimated"` (engine-owned connection) | The ordinary plan runs first with a time budget. If it finishes in time, nothing else happens and the cost is the cost of the ordinary plan. If it doesn't, the engine retries with the indexed plan, and every later statement of the request uses it. |

Without an exact count, `EXPLAIN` can't tell a rare term from a common one, so a rare term would make PostgreSQL read the whole sort index. The time budget catches that case. It is `search.planBudget`, 25 ms by default:

```ts twoslash
// ---cut-start---
import type { ResourceQuerySearchConfig } from "drizzle-resource";
// ---cut-end---
const search = {
  allowed: ["reference", "customer.name"],
  planBudget: 25,
} satisfies ResourceQuerySearchConfig<"reference" | "customer.name">;
```

What it costs, in either direction:

- A common term pays nothing beyond a transaction that sets the timeout, about one extra millisecond of round trips on a local database.
- A rare term pays the budget plus the indexed query, instead of reading the whole sort index: 25 ms plus a few milliseconds, against hundreds.
- A term in between that needs longer than the budget on the ordinary plan pays the budget and then the indexed query, which can be slower than letting the ordinary plan finish. Raise `planBudget` when your typical ordinary page takes longer than 25 ms.
- The budget never exceeds a `statement_timeout` already in force on the connection.
- Inside your own transaction (`db: tx`) there is no budget. The engine prices both plans with `EXPLAIN`, as it does for an exact count, because a timeout there would apply to every statement running on the same connection.

See [Performance](/scale/performance).

Keep `defaults` short: every default field adds a condition to every search, and many-to-many paths add a subquery each.
