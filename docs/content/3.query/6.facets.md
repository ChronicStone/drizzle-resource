---
title: Facets
description: Bucket counts for filter sidebars, computed in the same request as the page.
---

A facet counts the matching rows per value of one field: "612 shipped, 231 pending". Facets are requested with the page and use the same scope, filters and search.

```ts twoslash
// @noErrors
import type { QueryRequest } from "drizzle-resource";

const request: Pick<QueryRequest, "facets"> = {
  // ---cut---
  facets: [
    { key: "status", mode: "exclude-self", limit: 10 },
    { key: "customer.name", mode: "include-self", limit: 20 },
  ],
};
```

| Field   | Meaning                                                        |
| ------- | -------------------------------------------------------------- |
| `key`   | A field path in the resource's `facets.allowed`.               |
| `mode`  | Whether this facet's own filter applies to its counts (below). |
| `limit` | The number of buckets to return, largest first.                |

Leave `facets` out and no facet query runs.

## `exclude-self` and `include-self`

The example below filters on `status: shipped` and asks for the status facet with `exclude-self`: it still lists every status, so the sidebar keeps showing the other options. Change `mode` to `include-self` and only `shipped` remains.

::live-query{title="A status filter with an exclude-self status facet" :request='{"filters":[{"type":"condition","key":"status","operator":"is","value":"shipped"}],"facets":[{"key":"status","mode":"exclude-self","limit":10},{"key":"orderLines.product.category","mode":"exclude-self","limit":10}]}' :show='["facets", "sql", "rows"]'}
::

| Mode           | This facet's own filter | Use it for                                                 |
| -------------- | ----------------------- | ---------------------------------------------------------- |
| `exclude-self` | ignored                 | Filter sidebars: users can still see and add other values. |
| `include-self` | applied                 | Drill-down: show only what remains after the filter.       |

`exclude-self` only removes the client's filter on that field. The scope always applies.

## The response

```ts twoslash
// @noErrors
import { result } from "./twoslash-support";
// ---cut---
result.facets = [
  {
    key: "status",
    status: "ok",
    options: [
      { value: "pending", count: 12 },
      { value: "processing", count: 4 },
      { value: "shipped", count: 31 },
    ],
    total: 3,
  },
];
```

`total` is the number of distinct values in the filtered result, whatever the `limit`, so the interface can show "10 of 47".

`status` is always present:

| `status`    | Meaning                                                                                      |
| ----------- | -------------------------------------------------------------------------------------------- |
| `"ok"`      | The buckets are complete.                                                                    |
| `"skipped"` | The count hit its cap and the resource sets `whenCapped: "skip"`. `reason` is `"above-cap"`. |
| `"timeout"` | The facet exceeded `timeouts.facets`. It comes back with empty `options`.                    |

## Facets on big results

Facets read every row that matches, so they grow with the result. Two settings keep them from running on results that are too big to bucket:

```ts twoslash
// ---cut-start---
import type { ResourceQueryFacetsConfig, ResourceQueryTimeoutsConfig } from "drizzle-resource";
// ---cut-end---
const facets = {
  allowed: ["status", "customer.name"],
  whenCapped: "skip",
} satisfies ResourceQueryFacetsConfig<"status" | "customer.name">;

const timeouts = { facets: 2_000 } satisfies ResourceQueryTimeoutsConfig;
```

- `whenCapped: "skip"`: when the request uses a `capped` or `estimated` count and the matches exceed the cap, facets aren't computed and each requested facet comes back with `status: "skipped"`. The default is `"run"`. An `exact` or `none` count never skips facets.
- `timeouts.facets`: a facet that takes longer than this many milliseconds comes back with `status: "timeout"`.
- A count that times out counts as above the cap: with `whenCapped: "skip"` the facets are skipped.

## The SQL

Each facet groups the filtered rows by its field:

```sql
SELECT field_value, count(*) AS count
FROM root_table
[joins for the relation path]
WHERE [scope + client filters, minus this facet's own filter in exclude-self mode]
GROUP BY field_value
ORDER BY count DESC
LIMIT :limit
```

On PostgreSQL, facets with the same filters and joins can share one `GROUPING SETS` statement, or each facet can run as a statement of its own. [One statement or one per facet](#one-statement-or-one-per-facet) explains which one the engine picks.

| Facet field                                     | Cost                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------- |
| Root column (`status`)                          | No join. The cheapest.                                            |
| Many-to-one (`customer.name`)                   | One join. Fast with an index on the join column.                  |
| Through to-many (`orderLines.product.category`) | Junction joins and `count(distinct)`. Measure before allowing it. |

## One statement or one per facet

PostgreSQL cannot use parallel workers for a `GROUPING SETS` statement, so facets that share one are counted by a single CPU. A statement with one facet can be split across workers, and several of them overlap. Sharing wins on small results, where each extra statement costs more than it saves, and when a narrow filter leaves few rows to count.

The engine decides per request with `facets.splitAbove`, the number of rows the facets are expected to read. Above it, every facet gets its own statement and at most four run at a time. The exact count of a page is a statement of its own then, running next to them.

```ts twoslash
// ---cut-start---
import type { ResourceQueryFacetsConfig } from "drizzle-resource";
// ---cut-end---
const facets = {
  allowed: ["status", "customer.name"],
  splitAbove: 100_000, // the default
} satisfies ResourceQueryFacetsConfig<"status" | "customer.name">;
```

- The estimate is the root table's `pg_class.reltuples`: PostgreSQL's own count from the last `ANALYZE` or autovacuum. It is read once per table and reused for five minutes, so a table that grows is noticed.
- A request that filters or searches is judged by the planner's estimate of the rows it matches. A scope or filter that leaves 1% of a large table keeps one shared statement; that costs one `EXPLAIN`, about 0.3 ms.
- When PostgreSQL has no estimate (a table that was never analyzed, a view), the engine shares one statement.
- `0` always splits and `Infinity` never does. Neither reads any estimate.
- Inside a transaction you pass in with `db`, the statements follow each other on its one connection. Splitting still wins above about 200,000 rows there, because each statement can use workers; below that it is a draw, so raise `splitAbove` for resources you mostly query inside transactions.
- Each split facet has its own `timeouts.facets` budget: one that times out no longer takes the facets that shared its statement down with it.

Results are identical either way: options, `total`, `missing`, ordering, `limit`, `cursor`, `status`. `explain()` shows the statements that run, and `onQuery` reports the row estimate as a `plan` statement.

Measured on PostgreSQL 18 with 4 CPUs and an `orders` table with a `customers` relation, medians of 11 alternating runs on a busy machine, `count: "exact"` with a page:

| Request                           | 200,000 rows | 1,000,000 rows | 2,000,000 rows |
| --------------------------------- | ------------ | -------------- | -------------- |
| 2 root-column facets              | 25 → 13 ms   | 115 → 35 ms    | 230 → 88 ms    |
| 2 root + 2 relation facets        | 95 → 46 ms   | 281 → 186 ms   | 390 → 322 ms   |
| a page and 2 root-column facets   | 30 → 19 ms   | 114 → 39 ms    | 300 → 147 ms   |
| 2 root-column facets, 1% matching | 1.3 → 1.6 ms | 9.7 → 10.5 ms  | 18 → 18 ms     |

## Allowed facets

```ts twoslash
// @noErrors
import type { ExampleFacetsConfig } from "./twoslash-support";

const queryConfig = {
  // ---cut---
  facets: {
    allowed: ["status", "customer.name", "orderLines.product.category"],
  },
} satisfies { facets: ExampleFacetsConfig };
```

A facet key outside `allowed` is rejected with `Unknown facet field "…"`. Without `allowed`, every field path can be requested, so set it.

## Facets without the page

When a sidebar refreshes separately from the list, `queryFacets` computes facets without loading the page:

```ts twoslash
// @noErrors
import { ordersResource, request } from "./twoslash-support";
// ---cut---
const facets = await ordersResource.queryFacets({
  context: { orgId: "acme" },
  request,
  facets: [{ key: "status", mode: "exclude-self", limit: 10 }],
});
```
