---
title: Schema Helpers
description: requestSchema and responseSchema for both Zod and Valibot, the override types that narrow a resource contract, and the core subpath's runtime contract helpers
---

`drizzle-resource/zod` and `drizzle-resource/valibot` export the same two builders: `requestSchema` and `responseSchema`.

Both read the resource's contract — its field registry, allowed search and facet fields, pagination modes, defaults, and limits — and emit a schema in the validator you already use.

## Subpaths

| Subpath                    | Exports                                                                                                                | Peer requirement            |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------- |
| `drizzle-resource`         | `createQueryEngine`, `createQueryFilterBuilder`, `defaultQueryValidation`, `resolveQueryRequestContract`, all 54 types | `drizzle-orm >= 1.0.0-rc.4` |
| `drizzle-resource/core`    | Identical re-export of the root                                                                                        | `drizzle-orm >= 1.0.0-rc.4` |
| `drizzle-resource/zod`     | `requestSchema`, `responseSchema`, `QueryResponseSchemaOverride`, `queryZodIntegration`                                | `zod ^4.4.3`                |
| `drizzle-resource/valibot` | `requestSchema`, `responseSchema`, `QueryResponseSchemaOverride`, `queryValibotIntegration`                            | `valibot ^1.4.2`            |

`zod` and `valibot` are optional peers — install only the one you use. The Zod range is `^4.4.3`, and Zod 3 will not work.

The `/core` subpath exists so every entry point is symmetrical. It resolves to the same module as the root, so importing from either is equivalent.

## `requestSchema(resource, override?)`

Build a strict transport schema for the request body:

::code-group

```ts twoslash [zod.ts]
import type { QueryRequestInput } from "drizzle-resource";
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource } from "./twoslash-support";

const ordersRequest = requestSchema(ordersResource);

export function parseOrdersRequest(body: unknown): QueryRequestInput {
  return ordersRequest.parse(body);
}
```

```ts twoslash [valibot.ts]
import type { QueryRequestInput } from "drizzle-resource";
import { requestSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./twoslash-support";

const ordersRequest = requestSchema(ordersResource);

export function parseOrdersRequest(body: unknown): QueryRequestInput {
  return v.parse(ordersRequest, body);
}
```

::

Both `requestSchema` implementations are declared as returning `any`, so annotate the parse result as `QueryRequestInput` to keep the handler typed.

### What it validates

The schema is a **strict object** with five keys, so an unknown key is an error rather than a silent strip. That includes `context` — trusted state belongs in the sibling `context` argument, never in the body.

| Key          | Rule                                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------- |
| `pagination` | Union of the offset and cursor shapes, then refined against the resource's allowed modes             |
| `sorting`    | Array of `{ key, dir }`; `key` must be a sortable registered path                                    |
| `filters`    | Recursive `condition` / `group` union; `key` must be a registered path, `operator` one of the eleven |
| `search`     | `{ value, fields }`; every field must be in the resource's `search.allowed`                          |
| `facets`     | Array of `{ key, mode?, search?, limit?, cursor? }`; `key` must be in `facets.allowed`               |

Zod builds the filter node as a `z.discriminatedUnion("type", …)` inside `z.lazy`; Valibot uses `v.variant("type", …)` inside `v.lazy`. The accepted JSON is identical.

### What it defaults

Every key except `facets` carries a default, so `{}` parses into a complete request. For a resource whose defaults are cursor pagination, a `createdAt desc` sort, and two search fields:

```json
{
  "pagination": { "mode": "cursor", "cursor": null, "pageSize": 25, "count": "none" },
  "sorting": [{ "key": "createdAt", "dir": "desc" }],
  "filters": [],
  "search": { "value": "", "fields": ["reference", "customer.name"] }
}
```

An empty `sorting` array and an empty `search.fields` array are also replaced by the resource defaults, so a client can send `[]` and still get the resource's ordering and searchable columns.

`facets` has no default. Omit it and the key is absent, which is what skips the facet stage entirely.

### Where the limits land

The six limits become schema constraints:

| Limit             | Default | Constraint                                                            |
| ----------------- | ------- | --------------------------------------------------------------------- |
| `maxPageSize`     | 100     | Maximum `pagination.pageSize`, both modes                             |
| `maxCursorLength` | 2048    | Maximum `pagination.cursor` length                                    |
| `maxFilterDepth`  | 5       | Refinement on `filters`, message `Filter tree cannot exceed 5 levels` |
| `maxFilterNodes`  | 50      | Maximum length of the top-level `filters` array                       |
| `maxFacetCount`   | 10      | Maximum length of the `facets` array                                  |
| `maxFacetLimit`   | 50      | Maximum `limit` on each facet request                                 |

`maxFilterNodes` is the one asymmetry — the schema applies it to the top-level array length, while the engine counts every node in the tree. The engine check is the stricter of the two and runs even when no validator is used.

## `QueryRequestSchemaOverride`

Pass an override as the second argument to narrow one endpoint without redefining the resource:

```ts twoslash
import { requestSchema } from "drizzle-resource/zod";

import { ordersResource, type MyFieldPaths } from "./twoslash-support";

const exportFilters = ["status", "createdAt", "customer.name"] satisfies readonly MyFieldPaths[];

const exportRequest = requestSchema(ordersResource, {
  allow: {
    filters: exportFilters,
    sorting: ["createdAt"],
    search: ["reference"],
    facets: ["status"],
    pagination: ["cursor"],
  },
  defaults: { pagination: { mode: "cursor", pageSize: 100 } },
  limits: { maxPageSize: 200, maxFilterNodes: 10 },
});

export function parseExportRequest(body: unknown) {
  return exportRequest.parse(body);
}
```

That endpoint accepts three filter keys, one sort key, cursor pagination only — and still refuses a `pageSize` above 100.

::field-group
::field{name="defaults" type="ResourceQueryDefaultsConfig"}
Endpoint-local `pagination` and `sorting` fallbacks. `pagination` merges key by key with the resource's; `sorting` replaces it wholesale.
::

::field{name="limits" type="ResourceQueryValidationConfig"}
Endpoint-local ceilings. Each one resolves to the **lower** of the resource value and the endpoint value.
::

::field{name="allow" type="{ filters?, sorting?, search?, facets?, pagination? }"}
Per-axis allow lists. Each one **intersects** with what the resource already permits.
::
::

`allow` only narrows. A name the resource does not already permit is dropped from the intersection, so an endpoint can never widen a resource's surface. An empty array closes the axis completely.

Limits behave the same way. `maxPageSize: 200` against a resource that allows 100 resolves to 100 — `Math.min` is applied per limit, so an override cannot raise a ceiling.

::warning
The override's `allow` lists are typed as `readonly string[]` inside the validator packages, so a misspelled path is not a compile error — it silently narrows the axis. Anchor the list with `satisfies readonly MyFieldPaths[]` as above.
::

Two conflicts throw while the schema is being built, not on the first request:

| Condition                                                 | Message                                                                  |
| --------------------------------------------------------- | ------------------------------------------------------------------------ |
| A default sort key is outside `allow.sorting`             | `Default sorting field "createdAt" is not allowed for resource "orders"` |
| The default pagination mode is outside `allow.pagination` | `Default pagination mode "cursor" is not allowed for resource "orders"`  |

## `responseSchema(resource, override?)`

Build the response schema from Drizzle's select schemas plus the resource's relation tree:

::code-group

```ts twoslash [zod.ts]
import { responseSchema } from "drizzle-resource/zod";

import { ordersResource } from "./twoslash-support";

const ordersResponse = responseSchema(ordersResource);

export function assertPayload(payload: unknown) {
  return ordersResponse.parse(payload).pageInfo.mode;
}
```

```ts twoslash [valibot.ts]
import { responseSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./twoslash-support";

const ordersResponse = responseSchema(ordersResource);

export function assertPayload(payload: unknown) {
  return v.parse(ordersResponse, payload).pageInfo.mode;
}
```

::

Unlike `requestSchema`, this builder is fully typed — the parsed value narrows to the resource's row shape.

The emitted shape mirrors `QueryResponse`:

::field-group
::field{name="rows" type="Row[]" required}
One object per row, built with `createSelectSchema` for the root table and each declared relation.
::

::field{name="pageInfo" type="union of four objects" required}
Offset and cursor variants, each split by `count: "none"` and `count: "exact"`, so `rowCount` is `null` exactly when the count was skipped.
::

::field{name="facets" type="Facet[]"}
Optional. Each entry carries `key`, `options`, and the optional `nextCursor` and `total`.
::
::

Relations follow their cardinality: a `one` relation becomes a **nullable** object, a `many` relation becomes an array. The builder walks the resource's declared relation tree, so a relation missing from the relation graph throws `Unknown relation "customer" on table "orders"` while the schema is built.

The response object is strict — an extra top-level key fails. Row objects are plain objects, so an unexpected row key is stripped instead of rejected.

## `QueryResponseSchemaOverride`

Reshape a column or a nested relation without hand-writing the schema:

::code-group

```ts twoslash [zod.ts]
import { responseSchema } from "drizzle-resource/zod";
import { z } from "zod";

import { ordersResource } from "./twoslash-support";

const ordersResponse = responseSchema(ordersResource, {
  columns: { totalAmount: (amount) => amount.transform((cents) => cents / 100) },
  relations: { customer: { columns: { orgId: () => z.string().brand<"OrgId">() } } },
});

export function toEuros(payload: unknown) {
  return ordersResponse.parse(payload).rows.map((row) => row.totalAmount);
}
```

```ts twoslash [valibot.ts]
import { responseSchema } from "drizzle-resource/valibot";
import * as v from "valibot";

import { ordersResource } from "./twoslash-support";

const ordersResponse = responseSchema(ordersResource, {
  columns: {
    totalAmount: (amount) =>
      v.pipe(
        amount,
        v.transform((cents) => cents / 100),
      ),
  },
});

export function toEuros(payload: unknown) {
  return v.parse(ordersResponse, payload).rows.map((row) => row.totalAmount);
}
```

::

The override's output type flows into the inferred payload, so `row.totalAmount` stays a `number` while the branded `orgId` becomes a distinct type.

::field-group
::field{name="columns" type="Record<ColumnKey, (schema) => Schema>"}
One callback per column. It receives the generated schema for that column's type and returns the replacement.
::

::field{name="relations" type="Record<RelationKey, QueryResponseSchemaOverride>"}
The same override shape, applied to a nested relation. Nests as deep as the relation tree.
::
::

`columns` accepts only non-relation keys, and `relations` only relation keys — the two key sets are derived from the row type, so a typo does not compile.

::note
`QueryResponseSchemaOverride` is exported from each validator subpath rather than the root, because the callback signature is validator-specific. Import it from `drizzle-resource/zod` or `drizzle-resource/valibot`.
::

## Runtime contract helpers

Both helpers live at the root and at `/core`, and neither needs a validator installed.

### `defaultQueryValidation`

The six limit defaults, typed `Required<ResourceQueryValidationConfig>`. Spread it when you assemble a validation object and want every ceiling stated explicitly:

```ts twoslash
import { defaultQueryValidation } from "drizzle-resource/core";

import { engine } from "./twoslash-support";
// ---cut-before---
export const auditOrders = engine.defineResource("orders", {
  query: { validation: { ...defaultQueryValidation, maxFacetCount: 2 } },
});
```

A resource that omits `validation` resolves to exactly these values, so the spread changes nothing but the one key you set.

| Key               | Value  |
| ----------------- | ------ |
| `maxPageSize`     | `100`  |
| `maxCursorLength` | `2048` |
| `maxFilterDepth`  | `5`    |
| `maxFilterNodes`  | `50`   |
| `maxFacetCount`   | `10`   |
| `maxFacetLimit`   | `50`   |

### `resolveQueryRequestContract(resource, override?)`

The resolver both validator packages mirror. Use it to publish a resource's capabilities, or to build a schema for a validator this package does not ship:

```ts twoslash
import { resolveQueryRequestContract } from "drizzle-resource/core";

import { ordersResource } from "./twoslash-support";
// ---cut-before---
const contract = resolveQueryRequestContract(ordersResource, { allow: { pagination: ["offset"] } });

export const capabilities = {
  filters: [...contract.filters].sort(),
  sorting: [...contract.sorting].sort(),
  pagination: [...contract.pagination],
  limits: contract.limits,
};
```

Sending that object to the client removes the need to hard-code field lists in a table UI.

**Returns:** `QueryRequestContract` — `filters`, `sorting`, `search`, `facets`, and `pagination` as `Set`s, plus the merged `defaults` and the fully resolved `limits`. It applies the same intersection and `Math.min` rules, and throws on the same two default conflicts.
