description: Find the slow requests with onQuery, read one with explain(), fix it with checkIndexes() and an index or a copied column, then put limits on what grows with the table.
---

When a list endpoint gets slow, the time almost always goes to one of a few things: an exact count, facets, a sort through a relation, a deep offset page, or a search that matches most of the table. The engine has a tool for each step of finding and fixing them:

| Step                | Tool and what it gives you                                                                |
| ------------------- | ----------------------------------------------------------------------------------------- |
| [See](#see)         | `onQuery` on the engine: every statement, with its time and the shape of its request      |
| [Explain](#explain) | `resource.explain()`: the plan of each statement of one request, with warnings            |
| [Fix](#fix)         | `engine.checkIndexes()`: the sorts, scopes, searches and facets that no index serves      |
| [Guard](#guard)     | count modes, `whenCapped`, `timeouts`, `maxPageIndex`: limits that keep a request bounded |

Each tool returns plain data, so it works in a test or in CI as well as in a console. They all name a request by its shape: the resource, the filter, sort, search and facet keys, and the pagination and count mode. Values are left out. Two requests for the same screen with different filter values have the same shape.

The examples on this page ran on the benchmark's `orders` and `customers` tables. The resource is a typical order list:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
// ---cut---
const engine = createQueryEngine({ db, schema, relations });

const orders = engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    pagination: { modes: ["offset", "cursor"] },
    search: { allowed: ["reference", "customer.name"], defaults: ["reference", "customer.name"] },
    facets: { allowed: ["status", "paid", "customer.segment"] },
    sort: { defaults: [{ key: "createdAt", dir: "desc" }] },
  },
});
```

`orders` has a primary key and indexes on `(createdAt, id)` and `customerId`, plus trigram indexes for the two searched columns. The script that runs every example is [`tools/scale-examples.ts`](https://github.com/ChronicStone/drizzle-resource/blob/main/tools/scale-examples.ts).

## See: onQuery :span{#see}

`onQuery` is called after every statement the engine runs. The event has the statement's stage (`ids`, `count`, `rows`, `facets`, `summary`, `plan` or `scan`), its time in milliseconds, the SQL with `$1` placeholders, and the request's shape. Add up the time per shape and you know which kind of request costs the most, whatever values each one was sent with:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import type { QueryEvent } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
// ---cut---
type ShapeStats = { statements: number; ms: number; slowest: QueryEvent };
const byShape = new Map<string, ShapeStats>();

const engine = createQueryEngine({
  db,
  schema,
  relations,
  onQuery: (event) => {
    const stats = byShape.get(event.shape) ?? { statements: 0, ms: 0, slowest: event };
    stats.statements += 1;
    stats.ms += event.ms;
    if (event.ms > stats.slowest.ms) stats.slowest = event;
    byShape.set(event.shape, stats);
  },
});
```

Every request of a shape runs the same statements, so the slowest stage under each line points at the part to look at: facets and counts read every matching row, a sort by `customer.name` joins customers before it can sort, and page 4,000 reads all the rows before it.

In production, don't keep a map in memory. Send `event.ms` to your metrics library as a histogram labelled with `event.shape` and `event.stage`. A shape holds no values, so the number of label values stays bounded by the keys your resources accept. To log slow statements only, check `event.ms` against a threshold in the hook.

The hook cannot slow down or break a request: it runs after the statement has finished, an error it throws is ignored, and the engine does not wait for a promise it returns. See the [onQuery reference](/reference/on-query) for every field.

## Explain: resource.explain() :span{#explain}

Send a request of the slow shape to `explain()`. It builds the statements the engine would run for that request and runs `EXPLAIN` on each one. With `analyze: true`, the statements really run, inside a read-only transaction that is rolled back, so the report has measured times and row counts:

```ts twoslash
import { createQueryEngine, formatExplain } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
const orders = engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    pagination: { modes: ["offset", "cursor"] },
    search: { allowed: ["reference", "customer.name"], defaults: ["reference", "customer.name"] },
    facets: { allowed: ["status", "paid", "customer.segment"] },
    sort: { defaults: [{ key: "createdAt", dir: "desc" }] },
  },
});
// ---cut---
const report = await orders.explain({
  request: {
    pagination: { mode: "offset", pageIndex: 1, pageSize: 50, count: "exact" },
    sorting: [], // the default sort
    filters: [],
    search: { value: "", fields: [] },
    facets: [
      { key: "status", mode: "exclude-self", limit: 10 },
      { key: "paid", mode: "exclude-self", limit: 10 },
      { key: "customer.segment", mode: "exclude-self", limit: 10 },
    ],
  },
  analyze: true,
});

console.log(formatExplain(report));
```

::tool-output{name="explainList"}
::

Each line is one statement, listed in the order the request runs them: the count, one statement per facet, and the page. When PostgreSQL does something that grows with the table, the line says what it did, with the numbers from the plan, and the fix on the next line when the engine has one. A statement without a warning says how it reads its data, such as the page statement here, which reads 50 rows from the `(createdAt, id)` index.

The warnings `explain()` gives are `full-count`, `index-walk`, `seq-scan`, `deep-offset`, `misestimate`, `relation-sort` and `single-cpu-facets`. The [explain reference](/reference/explain#warnings) lists when each one fires.

Without `analyze`, nothing runs and the numbers are PostgreSQL's estimates. Use `analyze` on a replica or a copy of production data, since the statements cost their real time once. The report holds the plan, and the plan holds the request's values: log the shape, not the report.

## Fix: engine.checkIndexes() :span{#fix}

Some fixes are an index. Others change the schema or the resource. `checkIndexes()` compares what each resource lets a client ask for with the indexes of the tables behind it. Without `live`, it reads the Drizzle schema and needs no database, so it fits in a unit test:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
declare function test(name: string, run: () => void): void;
declare function expect(value: unknown): { toEqual(expected: unknown): void };
// ---cut---
test("sorts and scopes are indexed", () => {
  const errors = engine.checkIndexes().filter((finding) => finding.level === "error");
  expect(errors).toEqual([]);
});
```

With `{ live: true }` it reads the real indexes and table sizes from PostgreSQL and runs `EXPLAIN` on the default page query. On the example:

```ts twoslash
import { createQueryEngine, formatIndexFindings } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
// ---cut---
console.log(formatIndexFindings(await engine.checkIndexes({ live: true })));
```

::tool-output{name="checkLive"}
::

The first finding is about the sort options. Every root column is sortable by default, and five of them have no index: a client that sorts by `status` makes PostgreSQL read and sort every matching row for each page. Index the columns your interface sorts by (the finding prints the Drizzle index for each) and add the others to `sort.disabled`.

The second finding is the sort by `customer.name`. No index on `orders` can serve it, because the value lives in `customers`: PostgreSQL joins every order to its customer, then sorts. The fix is to copy the name onto `orders`, index the copy with `id`, and sort by it:

```ts twoslash
import { index, integer, pgTable, text } from "drizzle-orm/pg-core";
// ---cut---
export const orders = pgTable(
  "orders",
  {
    id: integer().primaryKey(),
    customerId: integer().notNull(),
    // a copy of customers.name, updated wherever a customer is renamed
    customerName: text().notNull(),
  },
  (t) => [index("orders_customer_name_id_idx").on(t.customerName, t.id)],
);
```

The copy is now a root column: sorting by `customerName` reads the index in order and stops after one page. The cost moves to your writes, which have to keep the copy current, in the code that renames a customer or with a trigger.

The last line is about the count, which no index can fix: the default count is exact, and an exact count reads every row that matches. That is what [Guard](#guard) is for.

When neither an index nor a copied column helps, two escape hatches remain: a [strategy](/scale/strategies) replaces the SQL of one step with your own, and a [virtual field](/resource/models) turns an SQL expression into a field. [Indexes](/scale/indexes) explains each rule `checkIndexes` applies and the indexes it suggests.

## Guard: caps and timeouts :span{#guard}

Some costs grow with the matching rows whatever you index. An exact count reads all of them, a facet groups all of them, and an offset page reads every row before it. Guards put limits on these in the resource definition, where a client can't lift them:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import {
  scaleDbAfter as db,
  scaleRelationsAfter as relations,
  scaleSchemaAfter as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
// ---cut---
const orders = engine.defineResource("orders", {
  relations: { customer: true },
  query: {
    pagination: { modes: ["offset", "cursor"], countCap: 10_000 },
    defaults: { pagination: { mode: "offset", count: "capped" } },
    search: { allowed: ["reference", "customer.name"], defaults: ["reference", "customer.name"] },
    facets: { allowed: ["status", "paid", "customer.segment"], whenCapped: "skip" },
    sort: { defaults: [{ key: "createdAt", dir: "desc" }], disabled: ["customer.name"] },
    validation: { maxPageIndex: 400 },
    timeouts: { count: 500, facets: 2_000 },
  },
});
```

- `count: "capped"` stops counting after `countCap` matches. When more rows match, `rowCount` is the cap and `exact` is `false`, and the interface shows "10,000+". The cap is part of the resource definition, and a client can't change it. `"estimated"` reads PostgreSQL's row estimate instead ("about 8.5M") and falls back to a capped count when the estimate can't be trusted.
- `facets.whenCapped: "skip"` skips the facets when a capped count hits its cap: each facet comes back with `status: "skipped"`. Counts per value over more rows than anyone pages through rarely help the person looking at the page, and narrowing the filters brings the facets back.
- `timeouts` bound each stage in milliseconds. A stage that runs out degrades instead of failing the request: the count becomes `none` with `reason: "timeout"`, a facet comes back with `status: "timeout"`.
- `validation.maxPageIndex` rejects offset pages past 400. Deep pages are for "load more" and exports, and cursor pagination reads them at the cost of the first page.
