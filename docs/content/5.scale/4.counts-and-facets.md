A page reads as many rows as it shows. A count, a facet or a summary reads every row that matches, because its answer depends on all of them. On a small result that costs nothing; on a table that keeps growing, these are the requests that grow with it. This page covers what each one costs and the settings that bound it. The request and response types are in [Pagination](/query/pagination#counts) and [Facets](/query/facets).

## Count modes

| `count`       | What it reads                                  | `pageInfo`              | Use it for                               |
| ------------- | ---------------------------------------------- | ----------------------- | ---------------------------------------- |
| `"exact"`     | every matching row                             | `rowCount`              | "page 4 of 12" when results stay small   |
| `"capped"`    | matching rows until `countCap + 1` of them     | `rowCount`, `exact`     | "10,000+" on big tables                  |
| `"estimated"` | no rows: PostgreSQL's estimate for the filters | `rowCount`, approximate | "about 8.5M" when a rough size is enough |
| `"none"`      | nothing                                        | `rowCount: null`        | feeds, "load more", exports              |

Offset pages count `"exact"` by default and cursor pages `"none"`. Set the default for a resource in `defaults.pagination.count`, and let a request ask for another mode when a screen needs it.

The count statement alone, on the benchmark's tuned schema, exact and capped at 10,000:

::bench-arrows{source="counts" :keys='["all","searchCommon","searchCustomer","relationSearch","ids","rareCustomer","rareReference","noMatch"]' title="The count statement, exact and capped"}
::

A capped count stops as soon as it has found 10,001 matches. When most of the table matches, that happens within the first rows it reads, and the count takes the same time at 200,000 rows as at 10 million. When few rows match and no index serves the search, PostgreSQL has to look through everything to find them, and a capped count costs what an exact one does: the cap only saves work when there are more matches than the cap. For those requests the cost is in finding the rows, and an index on the filter or search is what makes them faster.

With the trigram indexes in place, a rare term is the opposite case: the capped count is slower than the exact one. A capped count first runs the ordinary plan under `search.planBudget` (25 ms by default), and a rare term runs past it before the indexed plan answers. An exact count compares the cost of both plans up front and goes straight to the indexed one. One customer's orders take :bench-num{path="counts.rareCustomer.exact.ms" n="200k"} exact and :bench-num{path="counts.rareCustomer.capped.ms" n="200k"} capped at 200,000 rows, and a lower `planBudget` shortens the difference. [Search](/query/search#the-sql) describes the attempts.

`"estimated"` reads no rows: it asks PostgreSQL's planner how many rows the filters match. The planner's estimate can be far off for a filter or search through a relation, so in those cases, for an estimate at or below the cap, and on databases other than PostgreSQL, the engine uses a capped count instead. `pageInfo.count` tells you which one ran.

With any mode other than `"exact"`, offset pages fetch one row more than the page size to know whether a next page exists, so `hasNextPage` stays right.

## The cap

```ts twoslash
// ---cut-start---
import type { ResourceQueryConfig } from "drizzle-resource";
type ExampleQueryConfig = Pick<
  ResourceQueryConfig<any, any, any, any, any, any>,
  "pagination" | "defaults"
>;
// ---cut-end---
const query = {
  pagination: { modes: ["offset", "cursor"], countCap: 10_000 },
  defaults: { pagination: { mode: "offset", count: "capped" } },
} satisfies ExampleQueryConfig;
```

`countCap` belongs to the resource: a client can ask for a capped count but never choose the cap. It defaults to 10,000. Pick the largest number your interface shows exactly; past it, "10,000+" says as much as "8,549,540" to the person reading it. A higher cap costs more only on requests that match more rows than the cap.

## Facets

A facet groups every matching row by the value of its field, and returns the count of each value. It costs a full read of the matching rows, like an exact count, plus the grouping:

- A facet on a root column, such as `status`, groups the rows of the root table.
- A facet through a many-to-one relation, such as `customer.segment`, joins the related table first. Index the join column.
- A facet through a to-many relation joins the junction and counts distinct root ids. Measure it before you allow it in `facets.allowed`.

### One statement or several

On PostgreSQL, facets with the same filters and joins can share one `GROUPING SETS` statement, which reads the matching rows once and groups them every way at once. PostgreSQL can't use parallel workers for it, so one CPU does all the grouping. A statement with one facet can use workers, and several of them run at the same time on separate connections. Sharing wins on small results, where each extra statement costs more than it saves; separate statements win on large ones.

The engine chooses per request with `facets.splitAbove`, the number of rows the facets are expected to read:

```ts twoslash
// ---cut-start---
import type { ResourceQueryFacetsConfig } from "drizzle-resource";
// ---cut-end---
const facets = {
  allowed: ["status", "paid", "customer.segment"],
  splitAbove: 100_000, // the default
} satisfies ResourceQueryFacetsConfig<"status" | "paid" | "customer.segment">;
```

- Above `splitAbove`, every facet runs as its own statement, at most four at a time, and an exact count of the page runs as its own statement next to them. At or below it, facets share one statement.
- The estimate for a request without filters or search is the table's row count from PostgreSQL's statistics, `pg_class.reltuples`, read once per table and reused for five minutes. A request that filters or searches is judged by the planner's estimate of its matching rows, so a tenant or a narrow filter on a big table keeps one shared statement.
- A table PostgreSQL has never analysed has no estimate, and its facets share one statement. `0` always splits and `Infinity` never does.
- Inside a transaction you pass as `db`, the statements follow each other on its one connection. Raise `splitAbove` for resources you mostly query that way.
- With `timeouts.facets`, each split facet has its own budget, so one slow facet no longer takes the others down with it.

The answer is the same either way. `explain()` shows the statements that will run, and its `single-cpu-facets` warning, for a shared statement that reads many rows, suggests lowering `splitAbove`. [Facets](/query/facets#one-statement-or-one-per-facet) has the details.

The benchmark measured the four ways to run them on the tuned schema (the footnote says how). Above `splitAbove`, the engine runs them as in the last row: one statement per facet, in parallel.

Whichever way runs them, facets keep growing with the matching rows. The way to bound them is to not compute them when the result is too large to be useful.

### Skipping facets past the cap

```ts twoslash
// ---cut-start---
import type { ResourceQueryFacetsConfig } from "drizzle-resource";
// ---cut-end---
const facets = {
  allowed: ["status", "paid", "customer.segment"],
  whenCapped: "skip",
} satisfies ResourceQueryFacetsConfig<"status" | "paid" | "customer.segment">;
```

With `whenCapped: "skip"`, a request whose capped or estimated count hits the cap gets no facet counts: every requested facet comes back with `status: "skipped"` and `reason: "above-cap"`. The interface can show the filter options without counts, or ask the user to narrow the search. An exact count, or no count, never skips facets.

### When a facet is too expensive anyway

Some facets cost seconds even on a filtered result, typically a facet through a many-to-many relation on a large table. A custom `strategy.facets` won't make grouping through a junction table cheaper. Instead:

- pre-aggregate the counts in a table or a materialized view, and serve them with a [`strategy.facets`](/scale/strategies#strategyfacets);
- serve that one screen from a search engine such as Meilisearch or Typesense;
- load the facet in its own request, after the page, so the page doesn't wait for it.

## Summaries

A [summary](/resource/summaries) aggregates the matching rows into totals, such as a sum of amounts. Like a count, it reads every matching row whatever the page size. When the request also asks for an exact count, the summary statement supplies it. `timeouts.summary` bounds it, and `querySummary()` refreshes the totals alone when only the filters changed.

## Timeouts

A timeout per stage keeps one slow count or facet from holding a connection for seconds:

```ts twoslash
// ---cut-start---
import type { ResourceQueryTimeoutsConfig } from "drizzle-resource";
// ---cut-end---
const timeouts = {
  count: 500,
  facets: 2_000,
  summary: 2_000,
} satisfies ResourceQueryTimeoutsConfig;
```

A stage that runs out of time degrades and the page still comes back: the count becomes `{ count: "none", reason: "timeout" }`, the affected facets come back with `status: "timeout"`, and the summary with `summaryStatus: "timeout"`. A count that times out counts as above the cap, so with `whenCapped: "skip"` the facets are skipped too.

Each timed statement runs in a short transaction of its own on a pooled connection, so facets still run in parallel. A request holds one connection per statement while they run: up to four for split facets, plus its count. Inside a transaction you pass as `db`, the engine sets no timeout, because it would apply to everything on that connection. [Pagination](/query/pagination#timeouts) has the details.

Set the timeouts from what your screens can wait for, then watch `onQuery` for statements that come back with an error: those requests showed a degraded answer.

## Tenants

When a resource has a [scope](/resource/scope) on a tenant column, every count, facet and summary reads only that tenant's rows, provided an index starts with the tenant column ([Indexes](/scale/indexes#tenants)). Their cost grows with the tenant. The benchmark's scoped profile gives one tenant 1% of the rows:

::bench-arrows{source="scoped" :keys='["countExact","countCapped","twoFacets","relationSearch"]' title="The whole table and one tenant with 1% of the rows"}
::

An exact count inside a tenant can stay cheap long after it would be slow on the whole table. Size the limits for your largest tenant: a tenant with half the rows of a 10-million-row table costs what the whole table costs at 5 million. A scope through a relation (`customer.orgId`) loses this, since every query joins the related table first.
