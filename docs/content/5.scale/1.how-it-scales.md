---
title: How it scales
description: What stays flat as a table grows from 200,000 to 10 million rows, what grows with it, and what tuning does to each, measured on PostgreSQL 18.
---

::bench-note
::

A list request does up to three kinds of work. It finds the ids of one page, it loads the rows of those ids, and, when asked, it counts the matching rows, buckets them into facets or aggregates a summary. Finding and loading one page reads about as many rows as the page has, so it costs the same on a table of any size. Counting, bucketing and aggregating read every row that matches, so they grow with the table.

The numbers below come from the benchmark's `orders` table, with 20,000 customers, at three sizes. Each one is the median time of one request through the engine, from a single client. [How it was measured](/scale/benchmarks#how-it-was-measured).

## What stays flat

A page sorted by an indexed column reads 50 entries of the index and stops. A cursor page starts right after the last row of the previous page, however deep that is. A filter on a list of ids looks each one up.

::bench-scale{:keys='["page","cursor","ids"]' title="Flat as the table grows"}
::

These stay flat as long as an index serves the sort and the filters. [Indexes](/scale/indexes) says which ones to create, and `checkIndexes()` finds the missing ones.

## What grows

::bench-scale{:keys='["count","relationSort","twoFacets","fourFacets","searchCommon","relationSearch"]' title="Grows with the matching rows"}
::

- An exact count reads every row that matches. At 10 million rows, the page and its count take :bench-num{path="requests.count.outOfTheBox.ms"}, against :bench-num{path="requests.page.outOfTheBox.ms"} for the page alone.
- A sort by a related column, here `customer.name`, joins every matching order to its customer before it can sort. No index on `orders` changes that.
- A facet groups every matching row by its value. A facet through a relation also joins the related table.
- A search for a word that most rows contain matches the whole table. Finding a page of matches is fast, since the engine stops after 50, but the count reads all of them.

## What tuning does

Out of the box is the schema the benchmark starts with: primary keys, an index on `(createdAt, id)` and one on `customerId`, and trigram indexes on the searched columns. Tuned applies the fixes from [Optimize a slow page](/scale/optimize): a capped count, the customer name copied onto `orders`, and the facets setting the [setup table](/scale/benchmarks#how-it-was-measured) names.

::bench-arrows{:keys='["count","relationSort","twoFacets","fourFacets","searchCommon","searchCustomer","relationSearch","searchRareReference","searchRareCustomer"]' title="Out of the box and tuned"}
::

- A capped count stops after 10,001 matches, so every request with a count becomes as flat as a page.
- Sorting by the copied column reads an index in order, like any root column. An index on `customers (name)` alone leaves the join in place: [Indexes](/scale/indexes#relation-sorts) says why.
- Facets get faster but keep growing, because each facet still reads every matching row. `facets.whenCapped: "skip"` stops computing them past the cap, see [Counts and facets](/scale/counts-and-facets).
- The two rare searches are slower tuned at 1 and 10 million rows. Without an exact count, the engine measured here ran the page alone, and PostgreSQL walked the sort index row by row looking for the few matches. The current engine gives such a search `search.planBudget` milliseconds and then retries it with the trigram indexes; the next benchmark run measures that.

## Tenants

When a resource has a [scope](/resource/scope), every request reads only that tenant's rows, so its costs grow with the tenant. [Counts and facets](/scale/counts-and-facets#tenants) has the numbers for a tenant with 1% of the rows.

## Under load

The times above are one request at a time. Under concurrent load the gap widens, because counts and facets keep the database's CPUs busy while pages barely use them. [Benchmarks](/scale/benchmarks#under-load) has throughput at 32 concurrent callers.
