---
title: Custom strategies
description: Replace one step of the pipeline with your own implementation, and keep the rest of the engine.
---

A strategy replaces one step of a request with your code. The request and response shapes stay the same, and the other steps keep running as usual.

| Strategy | Built-in behaviour                                       | Replace it when                                        |
| -------- | -------------------------------------------------------- | ------------------------------------------------------ |
| `ids`    | One SQL query for the page's ids, and the count if asked | You need a different join shape or a hand-tuned query. |
| `rows`   | Drizzle relational query for those ids, in page order    | Rows come from another source or need another shape.   |
| `facets` | Grouped aggregates, one statement or one per facet       | Counts come from pre-aggregated data.                  |
| `query`  | The whole pipeline                                       | The staged model doesn't fit the endpoint at all.      |

Start with none. Most slow requests are fixed by an index, a copied column or a guard ([Diagnose & optimize](/scale/optimize)). Write a strategy when `explain()` shows a statement that none of those fix, and replace `ids` first: it is where most of the time goes. [Summaries](/query/summaries) need the built-in `ids` and `query` steps.

A strategy's statements are yours: `onQuery` doesn't see the SQL you run yourself, `explain()` refuses a resource with a custom `ids` or `query` step, and `checkIndexes()` skips their sorts and scope. The `utils` methods below report through `onQuery` like the engine's own statements.

## `strategy.ids`

```ts twoslash
// @noErrors
import { and, customers, count, db, eq, offsetPageInfo, orders } from "./twoslash-support";
// ---cut---
const strategy = {
  ids: async ({ request, context, utils }: any) => {
    const { pagination, sorting, filters, search } = request;
    const where = utils.buildWhereClause({ filters, search });

    return {
      ids: [],
      pageInfo: offsetPageInfo,
    };
  },
};
```

`request` is already normalized: the scope is merged, defaults are applied and every key is validated. `utils.buildWhereClause` compiles its filters and search to a Drizzle condition.

## `strategy.rows`

```ts twoslash
// @noErrors
const strategy = {
  rows: async ({ ids, relations, utils }: any) => utils.executeRowsQuery({ ids, relations }),
};
```

`ids` is in page order and `relations` is the load profile for this call. Return rows in the same order as `ids`, or use `utils.executeRowsQuery`, which loads, deduplicates and restores the order.

## `strategy.facets`

```ts twoslash
// @noErrors
const strategy = {
  facets: async ({ request, facets, context, utils }: any) =>
    utils.resolveFacets({ request, facets }),
};
```

## `strategy.query`

Replaces the whole pipeline. Use it only when the endpoint doesn't fit the ids, rows and facets steps:

```ts twoslash
// @noErrors
import { offsetPageInfo } from "./twoslash-support";
// ---cut---
const strategy = {
  query: async ({ request, context, relations, utils }: any) => ({
    rows: [],
    pageInfo: offsetPageInfo,
  }),
};
```

## Helpers

Every strategy receives `utils`, built from the resource's field paths, filter compiler and Drizzle setup:

| Helper                                        | Does                                                     |
| --------------------------------------------- | -------------------------------------------------------- |
| `utils.buildWhereClause({ filters, search })` | Compiles a Drizzle `where` condition.                    |
| `utils.compileOrderBy(sorting)`               | Compiles a Drizzle `orderBy` list.                       |
| `utils.executeIdsQuery(options)`              | Runs the built-in page-ids query and the count if asked. |
| `utils.executeRowsQuery({ ids, relations })`  | Loads rows by id in page order.                          |
| `utils.resolveFacets({ request, facets })`    | Runs the built-in facet aggregation.                     |
| `utils.resolveField(path)`                    | Returns the Drizzle column for a field path.             |

Using them keeps your step consistent with the rest of the engine. See the [strategy utils reference](/reference/strategy-utils).
