A page stays flat when PostgreSQL can read an index in the order of the sort, keep every row it reads, and stop after one page. Each section below is a case where that breaks, with the index or the change that fixes it and the finding `checkIndexes()` gives for it.

The examples use the `orders` table of [Optimize a slow page](/scale/optimize), which has indexes on `(createdAt, id)` and `customerId`. Each output keeps the findings about the case at hand: `checkIndexes` also lists every sortable column without an index (`sort-unindexed`) and a few `info` lines.

## The default sort

Most requests don't choose a sort, so the resource's default sort is the one to index first. The engine sorts by the request's sort and then by `id`, so that rows with equal values keep a stable order across pages, and filters by the scope. An index serves the default sort when it has, in this order:

1. the scope's equality columns, if any, in any order;
2. the sort columns, with the same directions, or all of them reversed (PostgreSQL reads a btree backwards);
3. `id`.

On a table without a scope, `(createdAt, id)` serves `createdAt desc`: PostgreSQL reads it backwards. Nulls must sort where the engine puts them, first on `desc` and last on `asc`. Drizzle's `.desc()` puts them last, so a nullable sort column needs `.desc().nullsFirst()`.

`default-sort-unindexed` is the one rule that reports an error, because it costs every request that doesn't pick a sort. Put this in a test so the error can't come back:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
declare function test(name: string, run: () => void): void;
declare function expect(value: unknown): { toEqual(expected: unknown): void };
// ---cut---
test("default sorts are indexed", () => {
  const errors = engine.checkIndexes().filter((finding) => finding.level === "error");
  expect(errors).toEqual([]);
});
```

## Tenants

A [scope](/resource/scope) such as `orgId = ctx.orgId` is part of every query. Put its column first in the index of the default sort:

```ts twoslash
import { createQueryEngine } from "drizzle-resource";
import {
  scaleDb as db,
  scaleRelations as relations,
  scaleSchema as schema,
} from "./twoslash-support";
const engine = createQueryEngine({ db, schema, relations });
// ---cut---
const orders = engine.defineResource("orders", {
  query: {
    scope: (f, ctx: { orgId: number }) => f.and([f.is("orgId", ctx.orgId)]),
    sort: { defaults: [{ key: "createdAt", dir: "desc" }] },
  },
});

orders.checkIndexes({ context: { orgId: 42 } });
```

With only `(createdAt, id)`, the check warns:

::tool-output{name="idxTenant" static}
::

PostgreSQL can still read `(createdAt, id)` in order and drop the rows of other tenants one by one. That is fine for a tenant that owns a good share of the table. For a tenant with 1% of the rows, it reads about a hundred rows for each one it keeps. With the tenant column first, PostgreSQL jumps to the tenant's rows and reads only those:

```ts twoslash
import { index, integer, pgTable, timestamp } from "drizzle-orm/pg-core";
// ---cut---
export const orders = pgTable(
  "orders",
  {
    id: integer().primaryKey(),
    orgId: integer().notNull(),
    createdAt: timestamp({ withTimezone: true }).notNull(),
  },
  (t) => [index("orders_org_id_created_at_id_idx").on(t.orgId, t.createdAt.desc(), t.id.desc())],
);
```

::tool-output{name="idxTenantFixed" label="Output with the tenant index" static}
::

The static check can't know how selective the scope is, so it warns. With `{ live: true }` it runs `EXPLAIN` on the default page query with your `context` and says what PostgreSQL chose:

::tool-output{name="idxTenantLive" label="Output with { live: true }"}
::

The tenant column also belongs on the root table. A scope through a relation, such as `customer.orgId`, joins the related table in every query, and no index on `orders` can serve it:

::tool-output{name="idxRelationTenant" static}
::

Copy the tenant id onto the root table, even when it is also on the parent. It never changes, so the copy costs nothing to keep current.

## Mixed directions

An index serves a sort when every direction matches, or every one is reversed. A sort such as `status asc, createdAt desc` mixes them, and no index on `(status, createdAt, id)` can serve it in either direction:

::tool-output{name="idxMixed" static}
::

Create the index with the same mix: the finding prints it.

## Relation sorts

A sort on a related column, such as `customer.name`, needs every matching order joined to its customer before PostgreSQL can sort. No index on `orders` can serve it. An index on `customers (name)` alone leaves the join in place: every matching order is still joined to its customer before PostgreSQL can sort, so the index only makes that join cheaper.

::tool-output{name="idxRelationSort" static}
::

::bench-arrows{:keys='["relationSort"]' title="Sort by customer.name, with the name copied onto orders and a capped count"}
::

Copy the column onto the root table and index it with `id`, as in [Optimize a slow page](/scale/optimize#fix). If you can't keep a copy current, add the related column to `sort.disabled`: a client that can't sort by it can't send the slow request.

## Text equality

Text filters ignore case, so a scope or filter `status = 'paid'` compiles to `lower(status) = 'paid'`. A plain index on `status` can't serve that:

::tool-output{name="idxTextScope" static}
::

Either index the expression `lower(status)`, as the finding prints, or add the field to `filters.caseSensitive`, which compares the column as it is and uses the plain index. Ids, codes and enums are good candidates for `caseSensitive`.

## Soft deletes

A scope that hides deleted rows, `deletedAt is null`, needs no index column, and an index column for it gets in the way: PostgreSQL does not treat `is null` as one value when it orders, so `(orgId, deletedAt, createdAt, id)` still makes it sort.

::tool-output{name="idxSoftDelete" static}
::

Leave `deletedAt` out of the columns. A partial index that holds only live rows is smaller and serves the scope exactly:

```ts twoslash
import { sql } from "drizzle-orm";
import { index, integer, pgTable, timestamp } from "drizzle-orm/pg-core";
// ---cut---
export const orders = pgTable(
  "orders",
  {
    id: integer().primaryKey(),
    orgId: integer().notNull(),
    createdAt: timestamp({ withTimezone: true }).notNull(),
    deletedAt: timestamp({ withTimezone: true }),
  },
  (t) => [
    index("orders_live_org_id_created_at_id_idx")
      .on(t.orgId, t.createdAt.desc(), t.id.desc())
      .where(sql`${t.deletedAt} is null`),
  ],
);
```

`checkIndexes` counts a partial index when the scope states its condition. If the scope can't promise it, for example because the condition depends on the context and you passed no `context`, the finding says it couldn't confirm the index is used.

## Search

Search compiles each field to `lower(column) like '%term%'`. Only a trigram index on the same expression can serve that, and the `pg_trgm` extension has to exist:

```sql
create extension if not exists pg_trgm;
create index orders_reference_search on orders using gin (lower(reference) gin_trgm_ops);
create index customers_name_search on customers using gin (lower(name) gin_trgm_ops);
```

With trigram indexes on every searched field, the engine can look up a rare term in the indexes first instead of walking the table: see [Search](/query/search#the-sql) for how it chooses. It never creates extensions or indexes itself, and it reads them when a resource first searches, so restart the process after adding them.

Static checks can't see expression indexes or table sizes, so `search-unindexed` is a live finding, for default search fields on tables of 100,000 rows or more:

::tool-output{name="idxSearchLive"}
::

Numbers and dates in a search are cast to text row by row, and no index helps. `search-numbers` points them out; keep them out of `search.defaults`.

## Small tables

On a small table an index barely matters and a plan says little: PostgreSQL may scan the whole table rather than read an index, and that is the right choice. Live mode doesn't run `EXPLAIN` below `largeTable.explain` estimated rows (10,000 by default; this example sets 50,000 so that it applies to a table of 20,000), or on a table PostgreSQL has never analysed, and says so:

::tool-output{name="idxSmallTable"}
::

The rules' verdict still stands, so a missing index on a table that will grow is reported now. Run `ANALYZE` after seeding a test database, or the live check skips every table.

## Static or live

|                  | `checkIndexes()`                     | `checkIndexes({ live: true })`                                   |
| ---------------- | ------------------------------------ | ---------------------------------------------------------------- |
| Reads            | the Drizzle schema and the resources | `pg_index`, `pg_class` and the plan of the default page query    |
| Indexes it knows | the ones declared in the schema      | the ones in the database, including those created by hand        |
| Needs a database | no, it returns synchronously         | yes, it returns a promise                                        |
| Extra rules      |                                      | `search-unindexed`, `exact-count-large-table`, `EXPLAIN` verdict |
| Good for         | a unit test on every commit          | a check against staging or a production replica                  |

Run the static check in your test suite and the live one where the data looks like production: an index that exists only in a migration shows up in the static check, and one created only in the database shows up in the live check. The [checkIndexes reference](/reference/check-indexes) lists every rule and option.
