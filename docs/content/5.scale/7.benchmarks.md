## Under load

The scaling runs above use one client. This run sent 32 concurrent callers through 10 pooled connections, with PostgreSQL held to 4 CPUs, on an earlier dataset of :bench-num{path="load.rows" format="count"} rows, on :bench-num{path="load.measuredOn" format="text"}.

::bench-bars{source="load" title="Throughput at 32 concurrent callers" caption="Yellow: no count and no facets."}
::

A page walks the sort index, takes 50 rows and stops. A count or a facet reads and groups every matching row, so under load those requests hold the database's CPUs while pages barely use them. Pages and cursors keep their p95, written under each bar, in single milliseconds with the pool fully busy. Cache, defer or [guard](/scale/optimize#guard) counts and facets before you add connections, since the database has the same CPUs either way.

Set the pool explicitly, with timeouts. A default pool can behave like three or four connections under load, and without timeouts one slow facet during a spike holds a connection that every other request waits for:

```ts twoslash
// @noErrors
import { Pool } from "./twoslash-support";
// ---cut---
// Example with the pg driver
const pool = new Pool({
  max: 10, // concurrent connections
  min: 2,
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 5000,
  statement_timeout: 10000, // stop any statement after 10 s
  query_timeout: 10000,
});
```

Start at 8 to 10 connections. Raise `max` when requests wait for a free connection. Slow statements don't get faster with more connections. On a big table one request can use up to four connections at once for its facets, plus one for its count: see [Counts and facets](/scale/counts-and-facets#one-statement-or-several).

## How it was measured

::bench-setup
::

Each request runs through the engine (`engine`), or as the SQL statement the engine would send, timed with `psql` inside the database container (`hand-sql`). The footnote under each table says which. Hand SQL leaves out the network and JavaScript, so compare numbers measured the same way.

Tuned values for requests with a count add two medians: the engine's page statement without a count, and the capped count statement run as SQL. The engine measured predates capped counts, so the count could not run through it. The facet comparison is SQL too: the engine of this run shares one `GROUPING SETS` statement between root facets.

## Run it yourself

The single-size harness is in the repository. It creates its own schema in the database you give it, checks that two engine versions return the same results, and alternates their runs:

```bash
TEST_DATABASE_URL=postgres://… \
BENCH_BASELINE_MODULE=…/drizzle-resource@2.4.1/build/index.js \
bun run benchmark:postgres
```

`BENCH_ROWS` and `BENCH_ITERATIONS` change the size, `BENCH_CONCURRENCY` sends several requests at once (the load section used 32, with the database container limited to 4 CPUs and one request type per process), `BENCH_SCAN=1` adds the full-export comparison, and `BENCH_OUTPUT` writes the JSON results.

Two scripts turn results into what these pages show:

```bash
# the numbers of the Scale pages, from tools/results
bun tools/scale-bench-data.ts
# fails when docs/app/data/bench-scale.json no longer matches tools/results
bun tools/scale-bench-data.ts --check

# the console output on Optimize a slow page and Indexes (creates and drops a database)
TEST_DATABASE_URL=postgres://… bun tools/scale-examples.ts
```

Use a database you can throw away, and give the container fixed CPUs and memory so runs compare.
